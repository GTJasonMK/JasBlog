用一个返回成功的仓储替身，订单测试可以很快通过，但它从未执行SQL，也就不可能发现事务句柄用错、唯一约束缺失或锁顺序冲突。选择测试层次，先问这次需要证明哪条规则，再决定替换哪些依赖。

## 测试分层

- 单元测试：活动时间、订单状态机、金额计算等纯业务规则。
- 存储集成测试：真实 MySQL 验证事务、唯一约束、查询与迁移。
- 组件集成测试：Redis Lua 和 Kafka 消费者使用隔离环境验证。
- 端到端测试：从 HTTP 发起抢购到查询订单，确认完整链路。

用 mock 时只替换外部边界，不要复制一份业务实现到 mock 中。数据库行为与内存 fake 不同，事务、隔离和 SQL 兼容性必须通过真实数据库覆盖。

活动开始点与结束点适合纯函数测试，输入固定时间即可。最后一件库存竞争要用两个独立事务，等待两边真正到达竞争位置，再同时继续；依靠随机sleep碰运气，容易出现没有竞争却被当成验证通过的情况。

事务测试不仅检查成功结果，还要在库存更新之后让订单插入失败，随后用独立查询核对库存没有减少。幂等测试同时发送相同键，检查只有一张订单和一次扣减；同键不同内容应明确冲突，不只断言接口没返回500。

## 测试数据和隔离

每个测试用独立 schema、前缀或容器，结束后清理。并行测试不可共享可变活动库存。外部依赖启动失败要使测试失败，不能静默跳过后报告通过。

如果集成测试被明确放在单独命令里，可以不在每次单测运行，但执行该命令时必须真正启动依赖并报告结果。不要连接失败就改用内存实现，否则报告看起来通过，实际需要验证的数据库路径却没有执行。

Kafka与Stream使用独立topic、group或受控命名，避免读取上次遗留消息。清理测试成果时只处理测试自己创建的资源，不能用全库清空方便下次运行。故障注入也局限于隔离环境。

## 把中断点写成可观察结果

消费者提交订单后、提交offset前退出，再重放同一event_id，订单数仍为1；relay收到Broker确认后、XACK前退出，再启动允许重复投递，但消费者不重复落库。每个中断点都检查最终业务结果与待处理记录，而不仅是函数是否返回。

端到端测试贯通一次请求、受理查询与最终订单，数量不宜用来替代大量规则测试。最终订单与库存勾稽、失败资源释放和超时取消，也需要各自明确断言。这样一次失败才能告诉我们哪条合同破坏了，而不是只剩“整条链没跑通”。

## 动手验证

为库存竞争写一个集成测试；再为 Redis 预扣失败、Kafka 发送错误、重复消费者事件各写一个测试场景。
