同时处理三份文件，不一定要让三段Python计算真正运行在三个CPU核心上。如果每个任务都花很多时间等待磁盘或网络，交错等待就可能缩短整体时间。反过来，三个任务都需要持续计算，只有真正利用多个执行单元，才有机会获得CPU并行收益。

并发描述多个任务的进度可以交错推进，并行描述它们在同一时刻使用多个执行单元。线程、进程和异步都是组织任务的手段，是否更快仍要看等待、计算和额外协调的比例。

## 线程方便共享，也容易共享得太多

下面用短暂等待模拟一个I/O阶段，只展示线程池怎样管理一组任务，不把它当成真实网络基准：

```python
from concurrent.futures import ThreadPoolExecutor
from time import sleep

def process_one(name):
    sleep(0.02)
    return f"已处理 {name}"

with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(process_one, ["a", "b", "c"]))
print(results)  # ['已处理 a', '已处理 b', '已处理 c']
```

线程共享进程内存，传入的列表、配置或客户端对象可能被多个任务同时使用。是否允许这样使用，要看对象的线程安全约定。涉及“检查当前库存再扣减”之类的复合动作，即使单个读写操作不会损坏容器结构，也不保证整个业务动作不可被插入。

可以使用 `Lock` 等同步原语保护共享规则，或者让每个任务处理自己的数据，通过结果返回汇总。共享越少，需要同时成立的状态约束通常也越少。

`pool.map` 按输入顺序提供结果，某一项抛出异常时，获取对应结果会看到失败。需要按完成顺序处理，可以使用 `submit` 得到future，再配合 `as_completed`。创建了future不代表错误已经处理，要实际获取结果或检查其状态。

## GIL 的结论要限定实现和构建方式

在启用GIL的常规CPython构建中，同一解释器内通常只有一个线程执行Python字节码。因此把纯Python的CPU计算拆成多个线程，常常无法得到多核计算收益。I/O等待期间可以释放执行机会，部分原生扩展也会在计算时释放GIL，所以线程仍可能有用。

Python还提供free-threaded构建，不应继续把“所有Python都一定有同样的GIL行为”当作前提。这类构建可以支持更多线程并行，但依赖是否兼容、扩展是否重新启用GIL，以及真实任务能否受益，都需要核对。官方说明见[自由线程Python](https://docs.python.org/3/howto/free-threading-python.html)。

不论哪种构建，都不能把GIL当作业务锁。一个业务动作由多个步骤组成，线程切换或外部调用可能发生在其中；free-threaded构建更要求依照明确的同步规则使用共享对象。

## 进程把状态分开，也增加传输成本

CPU密集任务可以评估进程池，例如将彼此独立的计算分配到不同进程。保存为独立脚本运行：

```python
from concurrent.futures import ProcessPoolExecutor

def square(value):
    return value * value

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=2) as pool:
        print(list(pool.map(square, [1, 2, 3])))  # [1, 4, 9]
```

这个任务很小，主要用于验证接口，不承诺比直接计算快。进程有启动、内存和数据传输成本；任务函数及参数也需满足进程启动方式与序列化要求。入口保护和可导入的顶层函数，使示例更适合跨平台使用，交互环境中的局部函数未必能这样直接提交。

各进程通常有各自的普通内存状态，修改子进程里的列表不会自动更新父进程那一份。需要通过返回值、队列或专门的共享机制交换数据。隔离减少某些共享风险，但错误汇总、任务取消和结果归属仍需设计。

## 并发数量需要与依赖容量对应

一个接口只有十个可用连接，启动一千个请求也不会变出更多容量，反而会增加排队、超时和内存。worker数量只是其中一个限制，等待队列、提交速度和每个任务的持续时间也要控制。不能一边无限提交任务，一边因为“线程池只有四个线程”就认为资源已经有界。

任务取消也不是强制终止已经运行的线程。网络请求要有自己的超时，长任务要有协作退出条件，退出线程池时还要确认待处理任务会怎样结束。任务启动之后，调用者仍然需要负责等待结果、传递失败和清理资源。

批量下载可以先评估有界线程池或异步I/O，纯Python计算可以评估进程池，图像压缩等原生库计算则需要查看库的行为后实测。选择依据放在任务真正消耗的资源上，就不会只凭一个“有GIL”或“能开进程”的标签下结论。
