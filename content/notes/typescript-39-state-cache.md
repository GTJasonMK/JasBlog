详情更新了任务，回到列表还是旧状态，常见原因是两边各保存了一份结果，却没有失效规则。缓存减少读取次数，同时也创建了一份可能过期的副本，关键是让它的归属和刷新条件明确。

输入框草稿、展开状态适合组件本地状态；跨页面共享的登录用户可由 Context 提供；任务数据来源于服务端，页面应有明确的加载、刷新和过期策略。

缓存能减少重复请求，但也产生失效问题。创建、修改、删除后要更新本地数据或重新请求。初版项目先用简单 Hook 和明确刷新动作，不引入复杂缓存库。

避免同时维护“服务端任务列表”和多份可编辑副本。表单提交前可保留草稿，成功后以服务端响应为准。

草稿不是服务器事实的无意义复制，它承载尚未确认的用户修改；提交失败应保留，成功后以规范化响应更新。列表缓存则按资源、当前用户、筛选、排序与页码组织键，遗漏身份或筛选可能把另一份数据错误复用。

新增后既可以把返回任务插入相应列表，也可以让相关列表失效后重查。前者要维护排序、筛选与分页总数，后者多一次请求但规则更简单；初版选择能完整维护的方案，不两种路径各写一半。

乐观更新先让界面变化，再等待服务器确认，需要保存原版本和失败回滚，还要处理多个请求交错。没有这项体验需求时，提交中明确等待、成功后刷新通常更容易保证一致。不能为“看起来快”丢掉失败与草稿。

组件重新渲染通常是正常过程。先用 React DevTools 或 Profiler 找到实际瓶颈，再考虑 memo、useMemo 和 useCallback；不要把它们当成默认写法。大型页面可用 lazy 与 Suspense 延迟加载路由，但要提供加载反馈。

useMemo缓存计算结果，不是持久存储，也不是让副作用只执行一次的合同。useCallback保持函数引用，在确有依赖或子组件比较需求时有用；它不会自动解决错误闭包。先消除重复状态与无界渲染，再按测量处理热点。

## 状态的归属和失效时机要明确

- 全局状态不等于所有状态都应该全局化。
- 缓存过期与数据一致性要明确。
- Context 更新会使使用它的组件重新渲染，注意状态边界。

退出或切换用户时清理与身份相关缓存，避免下一位用户短暂看到旧列表。刷新与失效测试应从详情回到列表、改变筛选、切换账号这些真实路径执行，不只检查某个setState被调用。
