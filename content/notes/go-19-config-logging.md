把超时写成 `2second`，解析失败后若忽略错误，就可能留下0。某些API里0表示没有超时，结果是一个拼写错误悄悄取消了资源边界。配置错误越早失败，越容易说明是哪项输入有问题。

## 配置

本地、测试和生产环境的端口、数据库地址、超时等配置不同，应通过环境变量或受控配置文件提供。配置加载时做显式校验，缺少必需值就启动失败。密码、令牌和私钥不能提交到仓库，也不应打印到日志。

配置先解析成明确类型，再检查范围：端口可用、池大小为正、关闭时限不超过平台宽限期。默认值只用于已经明确允许省略的配置，不在必填数据库地址缺失时悄悄连到另一台库。报错写字段名与原因，敏感字段不要带原值。

配置加载完成后再创建连接，确认必要依赖可用，再发布就绪状态。创建第三项资源失败，要关闭前两项已创建的资源；不要在每个包的init里各自连接外部服务，导致入口无法控制失败和清理顺序。

## 结构化日志

Go 标准库 slog 可输出结构化字段，便于日志平台过滤。日志要带请求 ID、路由、状态码和耗时；不要记录密码、完整认证头、支付密钥或未经脱敏的个人信息。

结构化字段的价值在于稳定查询，例如筛选 `request_id` 可以把一次入口、数据库错误与异步受理对应起来。路由标签使用模板 `/orders/:id`，避免把每个订单地址变成一个新维度；日志中的业务ID也应按访问权限和保留期限管理。

info记录有用的阶段结果，error记录需要处理的失败，debug用于受控诊断。每层重复打印同一个错误会制造数量假象；只记录“请求失败”又丢失原因。底层包装操作上下文，在合适边界输出一次，通常更容易追踪。

## 生命周期

服务启动后要能响应健康检查，并监听 SIGINT/SIGTERM。关闭时先停止接受新流量，再让正在处理的请求在限定时间内结束，最后关闭数据库、消息消费者等资源。清理函数应明确报错，不能静默忽略关键资源关闭失败。

~~~go
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := server.Shutdown(ctx); err != nil {
	return fmt.Errorf("shutdown http server: %w", err)
}
~~~

Shutdown使用独立的Background派生context，避免收到信号后沿用已经取消的服务context，导致清理立即结束。超时是给在途请求的上限，不保证它们一定完成；超过时限后的强制处理和退出状态也应明确。

HTTP停止接流量、在途请求结束后，再关闭它们依赖的数据库与发布器。消费者还要停止拉新任务、等待当前任务并处理offset；这些都不会因为HTTP关闭自动完成。日志最后记录哪些资源成功结束，清理失败则保留错误，便于判断下一次恢复是否需要补处理。

## 动手验证

定义端口、数据库连接地址和服务关闭超时三项配置。缺少端口或连接地址时让程序报出可理解的启动错误。
