一个字段叫 price 还不够：单位是元还是分，能不能为空，什么时候算最终结果，都应该明确。我会把这些约定和状态码一起作为客户端依赖的接口合同。

## 请求与响应模型

为 API 定义独立 DTO，不直接把数据库模型序列化给客户端。这样可以隐藏内部字段，也能独立演进存储和接口。字段命名、时间格式、金额单位和空值含义要在接口中固定。

统一响应可以包含 data 与 error，但不要为了统一而丢失 HTTP 状态码。错误响应至少要有稳定的机器可读 code 和适合用户阅读的 message；内部原因留在日志中。

用 OpenAPI 描述公开 HTTP 接口，可以生成文档、客户端或契约检查；规范文件也要进入版本控制并在 CI 中校验。生成代码不能替代对兼容性的判断：新增可选字段通常较安全，改字段类型、含义或必填性可能破坏旧客户端。

## 分页、过滤与版本

列表 API 应限制单页最大条数，排序字段使用白名单，避免用户任意拼接 SQL。简单数据可用 limit/offset；数据量大或持续变化的列表可评估游标分页。破坏兼容的字段和语义变化要通过版本或兼容迁移管理。

请求解析也要设资源边界：限制请求体大小、拒绝格式错误的数据，并对必填字段和未知字段制定一致策略。分页上限、批量操作数量和字符串长度都应有限制，避免合法格式的请求消耗无界资源。

## 幂等键

创建订单等可重试请求可以接收 Idempotency-Key。服务端要将键与用户、请求结果和有效期关联，并通过数据库唯一约束避免并发重复写入；仅在内存缓存键值不能提供跨进程保证。

## 动手验证

为创建订单定义请求 DTO、成功响应和三种错误 code：参数无效、库存不足、系统暂不可用。说明对应 HTTP 状态码。
