组件测试可以证明提交调用了createTask，却没有证明Cookie发到了API、数据库写入成功或资源授权正确。测试层次沿真实边界补齐，避免拿某一层通过推断整条链都成立。

Supertest 可直接对 Express 应用发请求。API 测试应覆盖有效输入、无效输入、未认证、越权和数据库约束。测试数据库与开发数据库隔离，并在每次测试后清理数据。

Playwright 从真实浏览器验证关键流程，如注册、登录、创建任务和退出。E2E 测试少而关键，细节逻辑放在更快的单元或 API 测试中。

Supertest对导出的app发送请求，不必在固定端口启动；测试会话时用独立agent保留各自Cookie。创建A和B，分别建任务，再让A读取、修改与删除B的任务，检查404或统一权限错误，并独立查询数据库确认没有改动。

验证请求校验时，绕过前端直接传空白标题、未知status、ownerId与空PATCH。否则页面控件已经挡住坏值，测试永远没有触及API真正该保护的入口。数据库唯一与外键则用真实隔离数据库，不用总返回成功的替身。

## 浏览器验证保留一条完整路径

从登录页输入凭据，创建带独特标题的任务，在列表找到，再刷新确认持久化；退出以后直接访问受限API应失败。测试根据可访问角色与明确文本定位，不用CSS层级锁住布局，也不靠任意sleep等待网络。

会话与数据按测试隔离，失败时保留请求、响应、页面截图和Trace等必要证据。环境启动失败应明确失败，不能捕获后当作通过；清理只处理测试创建的数据，避免删除开发者已有内容。

## 测试环境必须与真实用户数据隔离

- 不要让测试写入真实生产数据库。
- 测试通过不能证明所有安全问题不存在。
- E2E 失败时先区分应用故障、环境故障和选择器不稳定。

一条成功端到端流程证明关键接线可用，不代表所有输入与并发都被覆盖。把失败风险放到最小能观察到它的层次，回归会更快，故障也更容易定位。

## 动手验证

编写三类检查：未登录访问任务返回 401；用户 A 无法读取用户 B 的任务；浏览器登录后可新增并看到任务。
