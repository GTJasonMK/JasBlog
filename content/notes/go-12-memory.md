读入一个大文件，只留下前十个字节，为什么整个大数组还占着内存？如果留下的是原切片的一小段，它仍然引用原来的底层数组。垃圾回收看的是对象是否还可达，不按“业务只需要十个字节”自动切碎数组。

## 值与引用

数组、结构体等赋值通常会复制值；切片、映射、指针、channel 和函数值带有对运行时数据的引用语义。把一个结构体传给函数是否昂贵，取决于大小和编译器优化，先用基准测试确认。

Go的赋值与传参始终复制相应值。切片复制的是描述信息，里面的数组引用仍指向同一对象；结构体若含切片字段，也只复制这一层描述。需要保留很小一段且释放大数组时，可以复制这段元素到独立存储，让原引用离开存活范围。复制有成本，却可能缩短大对象生命周期。

Go 编译器会决定变量是否逃逸到堆上。可以使用 go build -gcflags=-m 查看优化与逃逸诊断。不要为了“避免堆分配”随意使用全局变量或复杂对象池；这会增加共享状态和维护成本。

返回局部变量的地址在Go中是合法的，编译器会让对象存活足够久，不能套用其他语言里“局部地址返回必然悬空”的规则。反过来，出现new或取地址也不能单凭语法确定最终堆分配，优化结果随调用方式、内联与版本变化。

值传递可能复制较多数据，指针则可能增加别名、逃逸和垃圾回收跟踪。选择应先看语义与对象大小，热点处再测量，不能把所有参数改成指针就声称优化完成。

## 垃圾回收

Go 的垃圾回收器自动回收不可达对象，但仍需控制对象分配率和长期持有引用。常见内存问题包括无界缓存、切片长期引用大数组、goroutine 泄漏持有请求数据。

GC无法回收仍被全局map持有的旧缓存，也不会替你关闭文件、连接或停止等待中的goroutine。内存持续增长可能来自保留关系，GC频繁则可能来自短命对象分配太多；二者需要不同处理。进程RSS还包含运行时、栈和其他映射，也不等于当前活跃Go堆大小。

对象池适合已经测出明显分配成本、且生命周期能够严格管理的场景。sync.Pool中的对象可以随时被清理，不能当永久缓存；放回前也要处理旧状态和大缓冲保留，避免一次大请求让长期内存预算改变。

## 诊断步骤

1. 用真实或接近真实的输入建立基准。
2. 用 CPU 或内存 profile 找热点。
3. 一次只改一个主要因素。
4. 重新压测并比较延迟、吞吐和内存。

性能剖析会在[第 36 章](/notes/go-36-performance)展开。这里重点是：先测量，再决定是否优化。

比较时记录输入规模、Go版本、运行参数和重复结果。一次改动同时更换算法、并发数和缓存，很难知道收益来自哪里。基准中也要消费结果，避免测到被优化器消除的空工作。
