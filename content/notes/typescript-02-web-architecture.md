点击新增，列表马上多一行，刷新却没了。可能只是改了浏览器内存，根本没有请求；也可能请求失败，界面仍提前显示成功。页面看得见，不等于数据已经持久保存，要沿实际数据流继续找。

浏览器负责展示页面并响应用户操作；服务端负责认证、业务规则和数据访问；数据库负责持久保存数据。浏览器不应直接连接生产数据库，也不能被当作可信环境。

典型请求流程：

1. 用户点击按钮。
2. 前端把输入转换成 HTTP 请求。
3. API 检查身份、权限和输入。
4. API 调用数据库并构造响应。
5. 前端根据响应更新界面。

静态文件由 Web 服务器提供；API 通常以 JSON 交换数据。前端代码可以被用户查看，因此秘密和权限判断必须放在服务端。

浏览器先取得HTML、样式与脚本，再执行事件逻辑。表单输入此时只是客户端状态；发出POST后，API解析请求、验证身份、规范化字段，并在数据库事务完成后返回结果。前端以返回的正式编号与时间更新列表，而不是假设本地临时值就是最终记录。

如果响应丢失，前端可能不知道数据库是否已提交。重复创建是否产生两份任务，由接口幂等合同决定；取消浏览器请求，也不会自动回滚服务器已经完成的提交。这些不是React状态管理库能单独解决的问题。

## 为什么浏览器不直接连数据库

浏览器代码与请求都可被用户修改，藏在脚本中的数据库密码最终也会交到用户手上。API把可信操作集中在服务端，按当前身份限制资源范围，数据库再用约束保护状态。前端检查空标题可以及时反馈，后端仍要拒绝绕过页面直接发来的非法请求。

数据库连接、业务权限与外部服务密钥留在服务端；真正要公开给浏览器的只是受控接口和公开配置。即使前后端都使用TypeScript，两边也是独立运行环境，不能通过共享一个类型就共享内存或信任。

## Python 对照

用 Python 写 Web 应用时，浏览器和服务器的边界依然存在。语言改变了，HTTP 请求、数据库和信任边界并没有改变。

一个全栈框架可能把页面和API放进同一个仓库，也可能在服务器生成HTML，但每段代码在哪里执行仍须分清。读文件、访问数据库的代码不能因为与组件同目录，就自然在浏览器里工作。遇到问题先确认执行位置，再核对输入和结果。
