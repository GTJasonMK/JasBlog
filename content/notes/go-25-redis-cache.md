商品详情读得很多、改得很少，把结果暂存在Redis可以减少数据库访问。但缓存里有旧价格时，不能只说“再更新一次”：一个较慢的旧查询，可能在新数据提交以后又把旧结果写回缓存。缓存问题往往来自两个系统的时序。

## 数据结构与用途

String 可保存计数器和简单值，Hash 可保存字段集合，Set 适合成员关系，Sorted Set 可做排序集合，Stream 可表达日志式事件流。选择结构前先明确访问模式和数据规模。

缓存旁路通常是：先读缓存，未命中时读数据库，再写入带 TTL 的缓存。TTL 应有合理范围；热点数据可以加入随机抖动，减少大量键同时过期。

~~~text
GET product:{id}
命中：返回缓存
未命中：读取 MySQL → 设置缓存 TTL → 返回结果
~~~

更新时要明确缓存失效策略。常见做法是在数据库事务成功后删除缓存；删除失败仍可能短暂陈旧，需要监控和重试机制。缓存不是主数据来源，丢失后应能从数据库重建。

先提交数据库再删缓存，避免新数据尚未存在时就让读者回源到旧值；但这仍不是跨系统原子操作。一个读请求可能早先读到旧数据库结果，稍后写回缓存，所以TTL、版本校验或受控重建要与业务可接受的陈旧窗口配合。不能把一个固定删除顺序称为绝对一致。

商品展示可能接受短暂陈旧，下单金额应重新按可信规则确认，库存是否足够更不能根据展示缓存判断。缓存层失败时是否回源，也要有容量预算：所有请求同时打到数据库，可能把局部故障变成整体故障。

## 键设计

键名应包含业务域和主键，便于排查；设置 TTL 和内存淘汰策略。避免把大对象或高基数用户数据无限放进 Redis。

大量键同时到期会形成集中回源，TTL抖动分散过期时刻；一个热点键失效时，可以按键合并并发加载，减少相同查询。不存在的对象也可短时间缓存空结果，但要区分缓存未命中与已经确认不存在，并考虑新建后如何失效。

String适合完整序列化的小对象，Hash适合按字段访问，Sorted Set适合带分数排序；选择同时考虑命令次数、单键大小与更新模式。大列表与大对象会增加单次处理和网络成本，不能只看总内存还剩多少。

## 持久化与高可用

缓存可以丢失并重建；库存预留等业务状态则必须明确 Redis 重启和故障切换后的恢复策略。RDB 与 AOF 在恢复时间、数据丢失窗口和写入开销上有不同取舍。副本提高读取能力和故障恢复能力，但复制通常是异步的；Sentinel 管理非分片主从故障转移，Redis Cluster 提供分片与分区级故障转移。选择哪种拓扑要结合数据量、可接受的数据丢失窗口和运维能力，不能把“有副本”当作零丢失保证。

如果预留只存在Redis，一次状态丢失可能重新售出已预留商品。此时它承担的是业务状态，不应再套用“丢了就从库重建”的缓存承诺。要记录预留生命周期、订单关联与对账依据，并说明数据库里究竟有什么足够恢复的信息。

## 动手验证

设计商品详情缓存键、TTL 和更新流程。说明缓存短暂陈旧对商品展示和库存扣减分别意味着什么。
