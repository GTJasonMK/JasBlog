登录成功只能说明身份得到确认。用户是否能查看某张订单，还得检查资源归属。我会把身份、权限、输入和凭据生命周期分开设计，逐条确认由哪里负责。

## 认证与授权

认证回答“你是谁”，授权回答“你能对这个资源做什么”。JWT 是一种令牌格式，不是加密方式；签名验证通过也不代表权限检查完成。验证时要检查签名算法、过期时间、签发方和受众，并设计密钥轮换。生产身份系统优先评估标准 OAuth 2.0 / OpenID Connect 服务，不自行发明密码协议。

密码应使用专门的慢哈希算法（如 bcrypt 或 Argon2 的成熟实现）保存，不能明文或用普通 SHA 哈希。敏感操作还要校验用户是否拥有目标订单。

还要定义令牌生命周期：访问令牌有效期、刷新令牌轮换、登出或泄露后的撤销方式，以及账号禁用后的生效时间。若用 Cookie 保存凭据，应设置 Secure、HttpOnly、合适的 SameSite，并评估 CSRF 防护；Bearer Token 放在 Authorization Header 时也要防止被日志和前端存储泄漏。TLS 应覆盖客户端到入口以及需要保护的内部链路。

## 输入与访问边界

SQL 使用参数化查询；URL 抓取等功能需防 SSRF；文件上传要限制大小和类型；登录和抢购需要按用户、IP 或资源做限流。跨域策略应使用允许列表，不能为图省事允许任意来源携带凭据。

CORS 是浏览器的跨域访问策略，不是服务端授权机制，也不能阻止非浏览器客户端访问 API。

## 机密管理

本地开发可以使用未提交的环境配置；部署环境用平台密钥管理能力注入。Kubernetes Secret 默认只是 API 对象，不等价于完整密钥管理；还需限制 RBAC、启用集群加密并避免把值写进镜像或日志。
