页面显示活动还在进行，点击时服务器时间已经越过结束点，价格也可能来自旧缓存。展示帮助用户选择，交易仍要按服务端当前有效规则确认，不能直接相信客户端回传的金额与状态。

## 业务边界

商品保存基础名称和状态；促销保存开始与结束时间、商品、限购数量和活动库存。请求进入时校验活动状态和用户资格。价格与商品信息应由服务端读取，不能接受客户端传入的价格作为结算依据。

## Handler 与业务服务

Handler 负责解析路径参数和身份，业务服务负责校验活动状态与调用存储接口，存储层负责 SQL。按这个顺序传递 context 和明确参数，不用全局变量共享数据库连接。

~~~go
type Campaign struct {
	ID        int64
	ProductID int64
	StartsAt  time.Time
	EndsAt    time.Time
	Limit     int
}

func (c Campaign) ActiveAt(now time.Time) bool {
	return !now.Before(c.StartsAt) && now.Before(c.EndsAt)
}
~~~

业务校验时间要注入或传入当前时间，方便测试边界时刻。生产项目也应考虑时钟来源、时区和活动配置变更。

ActiveAt采用左闭右开区间：now等于StartsAt时有效，等于EndsAt时无效。这样相邻活动可以在同一时刻交接，结束点不会同时属于两个区间。直接传now也避免测试依赖真实时钟，在开始前一瞬间和结束点都能稳定核对。

方法只回答时间是否落入区间，没有验证EndsAt晚于StartsAt、商品可售、活动未停用或用户满足资格。这些要在配置创建与下单流程各自对应的位置确认，不能从ActiveAt为true推导整次请求合法。

限购也不是只查“以前买过没有”。两个并发请求都可能查到没买过，最终需要数据库业务唯一约束或相应原子预留，把资格检查与写入关联。时间判断、身份、参与限制与库存分别维护不同规则。

活动中途允许改价吗？若允许，尚未成交的请求使用哪个版本，需要合同决定；订单已创建后则保存成交快照。可以冻结已开始活动的关键配置，也可以显式记录规则版本，不能在不同入口临时各读一份配置后声称同一次请求使用相同政策。

对于异步订单还要说明资格在哪个时刻确认：受理时有效的请求，落库时已经过结束点，是否继续完成？若按受理资格执行，事件和记录要保留经过确认的时间与规则版本，而不是消费者简单使用当前时间重新判定。

## 动手验证

测试活动开始前、开始时、结束前和结束时四个时间点；增加无效时间范围和限购量校验。
