订单逻辑接收gin.Context，读取全局数据库，再自己写响应，起初确实省事。后来只想测试“已取消订单不能付款”，却必须准备HTTP请求、路由和数据库，说明规则与运行环境已经绑到一起。

包应围绕一组稳定职责组织，而不是只按“文件类型”机械拆分。每个包尽量有清楚的输入、输出和依赖。Go 导入方向应从较外层的接口适配器指向业务核心；业务规则不应依赖 Gin、MySQL 驱动或 Redis 客户端。

订单函数接收普通Go值与context，返回业务结果和错误；HTTP把请求转成这些值，并映射响应；存储负责SQL与对象映射。需要保存能力时，由订单包声明小接口，让存储实现满足它，规则本身就能脱离框架测试。

一个中型服务可从简单布局开始：

~~~text
cmd/api/          程序入口与依赖组装
internal/order/   订单业务
internal/httpapi/ HTTP 路由和请求响应
internal/store/   数据持久化适配器
~~~

internal 目录限制其包只能被父目录范围内的代码导入。不要为了“标准结构”提前创建大量空目录；模块变大时再拆。

目录表达意图，import验证真实依赖。若order导入store，store又需要order类型，就容易形成Go禁止的循环。通常将接口和业务类型留在order，让store导入它，由入口接起来；不要靠不断膨胀的common包把环藏起来。

## 依赖注入

依赖注入可以是构造函数参数，不一定要引入容器。由入口组装 MySQL、Redis、业务服务和 HTTP Handler，再把需要的接口传进去。这样测试可以用内存实现替代外部系统。

`NewService(repository Repository)` 明确服务需要仓储，但不负责创建连接池。入口加载配置、创建连接、构造服务和路由；初始化失败就停止，并关闭已经创建的资源。关闭责任跟随创建责任，避免每层都认为别人会清理。

构造函数若要求十几个服务，应先检查对象是否承担过多职责，而不是先用容器隐藏参数。注入只解决依赖怎样提供，不解决业务划分错误。

## 包名要能说明职责

- 避免 utils、common 这类不断膨胀且职责模糊的包。
- 不要让业务包直接调用全局数据库连接；显式传入依赖更容易测试和关闭资源。
- 导出名称是公共 API，尽量只导出真正要被其他包使用的类型和函数。

纯计算可以保留普通函数，不必每个结构体都配接口、每次调用都套三层。只在替换、隔离或测试边界引入抽象；代码量小时，一两个职责清楚的包已经够用。

## 动手验证

把订单计算、HTTP 参数解析和数据库访问分成三个职责。画出依赖箭头，确保业务规则不依赖 HTTP 框架。
