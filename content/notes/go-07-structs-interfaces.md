我会先用结构体描述数据，再从调用者需要的行为里找接口。泛型适合保留通用算法中的类型关系，但业务规则各不相同时，专用函数通常更清楚。

## 结构体与组合

结构体把有关联的字段放在一起。Go 常通过嵌入和组合复用行为，而不是建立深层继承树。

~~~go
type Product struct {
	ID    int64
	Name  string
	Price int64 // 以分为单位
}
~~~

真实 API 中还要考虑字段校验、数据库模型和对外响应是否应该使用不同类型，避免把内部字段意外暴露。

## 接口

接口由方法集合定义，类型无需显式声明“实现了接口”。依赖方通常定义小接口，只暴露自己需要的能力。

~~~go
type PriceReader interface {
	PriceByID(ctx context.Context, id int64) (int64, error)
}
~~~

如果接口只有一个实现且没有测试或边界需求，不要过早抽象。接口的价值在于明确调用者需要什么，并允许替换外部依赖。

接口值同时包含动态类型和值。把一个 nil 指针赋给接口后，接口本身通常不等于 nil；这类 typed nil 是常见陷阱。判断接口错误时应直接用 err == nil、errors.Is 或 errors.As，而不是自行比较内部值。

## 泛型

泛型适合编写对多种类型都成立的通用算法和容器。若业务类型有不同规则，普通接口和专用函数通常更容易读。不要为了“泛型化”而把简单逻辑变复杂。
