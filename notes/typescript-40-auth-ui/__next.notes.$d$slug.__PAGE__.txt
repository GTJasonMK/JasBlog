React内存里初始user为null，不代表浏览器没有有效会话。立刻重定向登录，随后me接口又确认已登录，就会产生来回跳转。初始化先表达“尚未确认”，再根据服务端结果决定下一步。

页面打开时调用当前用户 API，得到已登录或未登录状态。登录成功后刷新用户状态并导航到任务页；退出时清除 UI 状态并调用服务端退出接口。使用 Cookie 会话时，浏览器在同源请求中自动发送 Cookie。

受保护路由只改善体验：未登录时引导去登录页。真正的权限仍必须由 API 验证。

会话检查至少区分等待、匿名、已登录与失败。me返回401可以按合同进入匿名；网络断开或500则是检查失败，不能静默当未登录，否则会误导用户重复输入凭据。受保护内容在确认前不呈现，同时给等待与重试留下明确位置。

登录成功后从服务端获得当前身份，刷新相关数据与缓存，再跳到允许的目标路径。保存返回地址时限制为应用内合法位置，不能直接把外部returnTo当成跳转目标。密码仅在提交所需范围使用，不写日志与持久本地存储。

## 退出到底退出了哪里

清空前端user只能改变界面，服务端会话仍可能有效。退出接口销毁或撤销会话并按相同Cookie属性清理凭据，客户端确认后清理身份相关缓存。退出失败要保留明确反馈，不能显示已退出却仍留可用会话。

HttpOnly Cookie不能由JavaScript读取，但浏览器仍按域、路径、SameSite与Secure等规则发送。同源fetch通常自动携带，跨源则需要credentials与服务端明确CORS配置；这不替代CSRF防护与资源授权。

## 会话状态需要从服务端恢复

- 不要把密码或会话秘密存入 localStorage。
- 页面刷新后不能只靠 React 内存状态判断登录。
- 加载当前用户期间，不要闪现受保护页面或错误重定向。

测试登录、刷新恢复、过期会话、me失败、退出与直接访问API。用户A的有效会话仍不能访问B的任务，这项限制在服务端查询里验证，而不是通过前端隐藏页面证明。

## 动手验证

实现登录、刷新页面保持会话、退出三条流程；手动访问任务 API 验证服务端仍会检查身份。
