响应里data可选、message也可选，类型会允许两者都没有，也允许失败却带成功数据。真正要表达的通常是二选一：成功一定有数据，失败一定有原因。联合类型把这种关系写出来，比不断补可选字段更准确。

interface 适合描述可扩展的对象形状；type 可以表示联合、交叉、原始值别名、元组和映射结果。二者都支持描述对象契约，团队应保持一致用法。

~~~ts
type TaskStatus = "todo" | "in_progress" | "done";

interface TaskSummary {
  id: string;
  title: string;
  status: TaskStatus;
}

type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; message: string };
~~~

联合类型表示多种可能中的一种；交叉类型组合多份要求。枚举会生成运行时代码；字符串字面量联合常更轻量且适合 JSON API。

检查 `result.ok` 为true后，检查器知道当前成员含data；为false时才读取message。共同字段ok作为判别，避免调用方自己猜“data存在就算成功”。T还保留了成功数据的具体形状，任务列表与用户信息可以复用相同结果结构。

TaskStatus限制静态代码使用三个字符串，但不在运行时拦截任意请求。解析外部状态时仍要检查名单，不能只把文本as TaskStatus。字面量联合适合已有明确文本协议，不必为了类型检查再引入一个有运行时表示的枚举。

## 对象声明与组合规则

interface可以描述对象并扩展，也支持某些声明合并场景；type可以给联合、元组和映射结果命名。普通对象用哪种通常按项目约定统一，避免把命名风格争论当作业务设计。

交叉类型要求同时满足两份约束。若一边把id写成string，另一边写成number，不会得到“二者任选”，反而可能得到不可满足的字段。组合后检查实际结果，别把交叉符号当作无条件拼接。

建模时优先减少不可能状态：加载中没有结果，成功有数据，失败有错误。后面的收窄与穷尽检查才能沿这些关系帮助发现遗漏；如果一开始全写成可选字段，编译器也无法替你还原隐藏的状态规则。

## 联合类型不能当作所有字段同时存在

- 联合类型的值不一定同时拥有各个成员的所有属性。
- 不要为了区别一个状态而强制使用数字枚举。
- 类型别名和接口不是完全可互换，组合语法不同。
