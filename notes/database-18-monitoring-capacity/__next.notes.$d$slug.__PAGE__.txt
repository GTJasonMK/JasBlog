我会先看请求成功率和延迟，再看连接、等待、SQL 与存储。CPU 不高时也可能已经锁住了整个下单流程，缓存命中率很高也可能只是反复扫描太多数据。

## 先监控业务结果

从请求成功率、事务延迟、超时、下单失败率和对账差异出发，再关联数据库证据。CPU 不高但锁等待严重时，服务依然可能完全无法下单；缓存命中率很高也不能证明扫描量合理。

| 维度 | 观察项 | 典型后果 |
|---|---|---|
| 连接 | 活跃、空闲事务、池等待、剩余连接 | 请求排队，管理员无法接入 |
| 等待 | 锁、I/O、客户端读写、事务年龄 | 尾延迟上升与资源长期占用 |
| SQL | 总耗时、调用次数、返回行数、计划变化 | 热点语句耗尽资源 |
| 存储 | 数据、索引、WAL、临时文件、剩余空间、延迟 | 写入失败或服务中断 |
| 维护 | 死元组估计、维护进度、XID 年龄 | 膨胀或防回卷紧急维护 |
| 复制与备份 | LSN 差、槽保留、归档失败、最后成功恢复 | 数据丢失或恢复目标无法兑现 |

告警阈值根据业务目标、历史基线、容量和增长确定，并附操作手册。备份任务“昨天成功”不等于恢复链今天有效，要同时监控日志连续性和周期恢复演练。

## 查看配置来源与生效条件

```sql
SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
WHERE name IN ('max_connections', 'shared_buffers', 'work_mem',
               'maintenance_work_mem', 'max_wal_size', 'archive_mode',
               'statement_timeout', 'idle_in_transaction_session_timeout')
ORDER BY name;
```

`context` 决定能在哪种范围修改，`pending_restart` 表示有设置等待重启。`ALTER SYSTEM` 修改配置文件并不意味着立刻生效；部分参数需要 reload，部分需要 restart。还要检查角色、数据库、会话层设置是否覆盖。

`work_mem` 是每个相关执行操作的预算，哈希等还可能受额外倍率影响；不能把它乘连接数后当作完整内存上限，也不能直接按“机器内存的一半”配置。测量并发计划、节点与实际内存。

`max_wal_size` 影响检查点策略，不是 WAL 占用绝对上限。归档失败、复制槽和高写入负载都可能让 WAL 继续增长。不要因为超出该值就删除 `pg_wal` 文件。

## 做能解释的容量预算

估算数据增长、索引比例、历史版本、WAL 保留、备份、临时排序和重写空间。假设每天新增业务数据 2 GB、索引约为数据的 50%，仅新增主体就约 3 GB/天；还未包含更新膨胀、日志和备份。

按不同磁盘卷分别计算“可用空间 ÷ 近期净增长速率”，得到粗略耗尽时间。大批回填、建索引或复制槽失活会改变增长速率，因此还需要变化率告警和操作前预算。

应用层请求预算要留出连接等待、执行、提交与网络时间。SQL 超时比接口总超时更长时，用户请求可能已经放弃而数据库仍在继续工作；取消和结果不确定都要有处理策略。

## 压测要有业务含义

固定版本、硬件、数据量、索引、参数分布、读写比例和事务内容，逐步增加并发，记录吞吐、p50/p95/p99、错误率、锁等待和资源。报告达到业务延迟目标时的吞吐，不只报告最高 QPS。

`pgbench` 可以测量指定事务脚本，但默认账户转账负载不代表你的订单系统。测试环境不能包含真实支付或外发消息，压测生成的数据要能区分并可核对。

## 动手验证

为示例数据库设计一页监控清单，给出连接耗尽、WAL 持续增长和备份过期的具体处置入口。提交一次 L4 五轮测量，并说明哪些结论受限于单机、小数据和缓存状态。
