Go 30：搭服务骨架：配置、依赖装配与健康检查

Go促销订单项目

目录

  • 推荐结构
  • 公共能力
  • 运行后检查
  • 动手验证

数据库地址拼错，程序照样监听端口，healthz返回200，第一位用户下单才发现连接失败。它启动了，却没有说明什么时候真正能工作。骨架先要把配置、依赖、接流量与退出的顺序确定下来。

推荐结构#

text
cmd/api/             启动入口与依赖装配
internal/config/     配置读取与校验
internal/httpapi/    Gin 路由、DTO、中间件
internal/order/      订单领域规则
internal/catalog/    商品与促销规则
internal/store/mysql/数据库适配器
internal/store/redis/Redis 适配器

main 函数负责加载配置、连接依赖、创建 Handler、启动 HTTP Server，并按相反顺序关闭资源。业务包不导入 Gin；存储接口由业务调用方定义，存储适配器负责实现。

目录按实际需要创建。入口只组装，订单状态留在order，SQL与驱动错误转换留在适配器。HTTP与worker有相同订单规则时，调用同一业务函数，避免两个入口复制后逐渐写出不同的库存判断。

创建连接池不一定已经连通，必要依赖要在受控超时内探测；失败停止启动，并关闭已经创建的资源。日志说明失败阶段，避免打印带密码的完整连接串。默认值只用于允许省略的配置，缺失必需地址不能悄悄换另一台库。

公共能力#

配置字段要有默认值和必填规则；日志使用结构化字段并加入 request_id；错误在 Handler 边界映射为稳定 API code。/healthz 只检查进程是否活着，/readyz 检查当前实例是否可以接收流量，两者不能混为一个始终返回成功的接口。依赖探测应反映实际服务能力：若某个降级路径仍可用，不要因为一个非关键依赖短暂失败就让所有 Pod 同时退出流量。

运行后检查#

存活探针不应简单绑定共享数据库，否则数据库故障可能触发所有实例不断重启，反而增加恢复压力。就绪表示当前实例能否按合同接新请求，阈值与频率也要避免瞬时抖动导致流量反复迁移。

退出先停止接新流量，等待在途请求，再关闭它们依赖的数据库和发布器。后台任务有独立取消与等待责任，HTTP Shutdown不会自动完成。退出结果要说明未完成事件是否会在下次启动恢复。

创建模块、启动 HTTP 服务、返回健康状态，并可通过 SIGTERM 优雅关闭。启动缺少数据库配置时应给出明确错误，而不是悄悄使用空配置。

再停止数据库，观察就绪和存活是否按预期变化，恢复后确认能处理请求。此时不需要完整商城，但要真正执行启动失败与正常关闭，不能只检查目录齐不齐。

动手验证#

为配置校验写表驱动测试；再创建一个不连接数据库的 Handler 单元测试。
