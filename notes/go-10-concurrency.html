Go 10：goroutine 与 channel：启动之外还要负责退出

Go语言与工具链

目录

  • goroutine 与 channel
  • select
  • 设计并发任务
  • 动手验证

函数前加一个go，它就可能与当前函数并发执行，调用方却不会自动等待。main返回时，进程结束，剩余任务不会因此获得完成机会。启动只是第一步，还要知道谁收结果、谁等待，以及何时不再需要它。

goroutine 与 channel#

goroutine 是 Go 运行时管理的轻量执行单元。创建 goroutine 很容易，但程序仍要负责等待它结束、传递错误和取消工作。channel 用于在 goroutine 间传递值；它不是自动保护所有共享状态的万能工具。

并发意味着执行过程可以交错，是否同时使用多个核心还取决于调度、可运行任务和硬件。网络等待期间让其他任务继续，可能提高资源利用；纯计算拆得太碎，调度与通信成本也可能超过收益。

go
func worker(jobs <-chan int, results chan<- int) {
	for job := range jobs {
		results <- job * 2
	}
}

接收方向和发送方向写在参数类型中，能让数据流更清晰。关闭 channel 的通常是发送方，因为发送方知道不再有新值；向已关闭 channel 发送会 panic。

worker会读jobs，直到它关闭且缓冲值已取完。每次发送results都可能阻塞：无缓冲通道要与接收配合，缓冲通道满时也会等待。只启动worker却没人接results，它就可能停在发送处，无法继续读任务。

关闭表示不再发送，不是销毁通道，也不是随意打断另一方。value, ok := <-results 能区分零值与结束；关闭且耗尽后，接收立即得到零值和false。nil通道的发送与接收则一直等待，这两种状态不能混淆。

select#

select 可等待多个 channel 操作之一，也可配合 default 做非阻塞尝试。若需要超时和取消，优先使用 context 的 Done channel，而不是在每个函数里自建计时器。

多个分支同时就绪时，select不保证业务优先级。带default的无限循环还可能忙等占满CPU；没有立即返回需求，就让它阻塞等待。任务接收和结果发送两个位置都可能阻塞，取消路径必须分别覆盖，不能只在循环顶部检查一次。

设计并发任务#

并发适用于彼此独立且有足够工作量的任务。用 sync.WaitGroup 等待一组 goroutine 结束；任务需要错误传播和统一取消时，可使用 golang.org/x/sync/errgroup。请求量无限时不能无限创建 goroutine；应限制并发数、队列长度和等待时间。数据库、外部 API 等依赖本身也有限制。

多个 goroutine 共同发送时，任何一个发送方都不能擅自关闭共享 channel；需要由协调者确认所有发送方退出后再关闭。阻塞发送和接收都应考虑 context 取消，否则上游退出后可能遗留 goroutine。

有界流水线可以这样分工：生产者投递完关闭jobs，固定数量worker处理，协调者用WaitGroup等所有worker退出后关闭results，调用方一直消费到通道关闭。错误要送回共同管理者，并触发其他任务的协作取消，不能报错以后直接遗弃阻塞中的发送者。

通道只保护交接。若传的是map或指针，交接后两边继续修改同一对象仍会竞争。应转移所有权、复制需要的状态或加锁。并发上限还要匹配连接池、外部配额与内存，启动一万个任务等同一个小连接池，只是把队列搬进了进程。

动手验证#

实现一个有界 worker pool：最多启动 3 个 worker，处理 10 个整数任务，收集结果并在所有 worker 退出后结束。再让其中一个任务返回错误，确保其余任务能取消并正常退出。
