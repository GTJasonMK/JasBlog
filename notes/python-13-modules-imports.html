Python 13：模块、导入与程序入口

一个脚本已经能计算平均值，另一个脚本也想用这个函数，于是写下 import stats。结果还没调用函数，程序就开始问用户输入。为什么导入一个定义，也会触发交互？因为导入模块时，模块顶层代码会执行。

模块通常对应一个 .py 文件，为相关定义提供自己的命名空间。拆分模块可以把计算、输入输出和启动流程分开，让同一个计算函数被命令行、测试或其他功能复用。但前提是它被导入时，不会立刻启动本来只属于独立运行的流程。

导入执行哪些代码#

在同一目录创建 stats.py：

python
# stats.py
def average(values):
    if not values:
        raise ValueError("至少需要一个数")
    return sum(values) / len(values)

再创建入口文件 app.py：

python
# app.py
def main():
    from stats import average
    print(average([3, 6, 9]))


if __name__ == "__main__":
    main()

运行 python app.py 会输出6.0；在别处 import app 则只定义 main，不执行它。直接运行文件时，__name__ 被设为 "__main__"，作为模块导入时则使用模块名，所以这条判断能够区分两种用途。

定义函数本身也是执行顶层语句，只是函数体要等到调用时才执行。类定义、默认参数表达式、装饰器同样可能在导入期间运行。把交互、启动服务、批量读写文件等动作放到明确入口，可以避免它们随一次普通导入发生。

这里把导入写在 main 内，是为了让两个文件的调用关系清楚；一般没有延迟加载需求时，也可以把 from stats import average 放在 app.py 顶部。关键在于被导入模块本身的副作用是否合理，不能靠把所有导入都藏进函数解决模块设计问题。

两种导入写法怎样影响名称#

import stats 在当前模块中绑定 stats，使用时写 stats.average(...)，来源很明确。from stats import average 则直接绑定 average 这个名称，适合来源清楚、使用频繁的对象。

但后者不会建立一个跟随外部名称变化的实时连接。如果另一个模块后来给 stats.some_value 重新赋值，已经通过 from stats import some_value 绑定的名称不会自动更新。若两边共同引用的是一个可变对象，它们仍然能看到该对象的修改，这与名称和对象的规则一致。

from module import * 把许多名称放进当前空间，容易覆盖已有名称，也难以看清依赖来源。业务代码通常明确列出导入项，不依赖这种隐式扩散。

同一解释器进程里，导入系统通常会从 sys.modules 复用已加载模块，顶层代码不会因为同一个模块再次普通导入就重新执行。重启程序是另一个进程，自然又会初始化；专门的重载操作也另有规则。因此不能把“只初始化一次”理解成整个系统永久只运行一次。

脚本名称可能遮住标准库#

模块查找会检查一定的搜索路径，这些路径与启动方式、安装环境有关。自己的目录里如果有个 json.py，import json 可能找到自己的文件，随后出现“模块没有 loads 属性”之类的错误。此时反复安装依赖没有意义，应先查看实际加载文件的位置，例如标准库模块的 json.__file__。

给脚本起明确的业务名称，可以避开 random.py、typing.py 等常见冲突。当前目录、项目包和解释器的第三方安装目录是不同概念，换一种启动方式后暴露的查找问题，也不宜靠到处追加 sys.path 掩盖。

文件多起来以后，用包表达归属#

普通包可以用目录加 __init__.py 组织相关模块：

text
project/
  study/
    __init__.py
    stats.py
    app.py

假设 study/app.py 使用 from .stats import average，这个点表示同一个包内的相对导入。从 project 目录执行 python -m study.app，导入系统知道 app 属于 study，就能正确理解这层关系。

直接执行 python study/app.py 时，文件通常被当作独立脚本，没有相同的包上下文，相对导入就可能失败。这里应当统一项目的启动方式，而不是一会儿改导入，一会儿复制函数。命名空间包可以没有 __init__.py，那是另一种组织方式，初学时先把普通包和 -m 的工作关系用清楚。

循环导入常暴露职责没有分开#

模块A需要B，B又在初始化期间读取A里还没定义完成的名称，就可能得到“部分初始化模块”的错误。导入并不是先把所有模块同时准备好，再一起运行，它有具体的执行次序。

这时应先看两边到底共享什么。如果只是共同使用一种数据结构，可以把这个定义放进独立模块，让A和B都依赖它；入口模块负责组装调用，下层计算模块不再反向导入入口。确有必要的延迟导入可以放到调用时，但它不替代对依赖方向的检查。

验证最开始的两个文件时，可以分别执行 python app.py 与 python -c "import app"：前者计算，后者不输出也不等待输入。这就说明程序启动与模块复用已经是两个可独立使用的动作。
