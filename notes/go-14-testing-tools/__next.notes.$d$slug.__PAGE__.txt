## 表驱动测试

测试文件以 _test.go 结尾，测试函数名以 Test 开头。表驱动测试适合用多个输入覆盖一个规则。

下面的片段放进同包测试文件并导入testing。每行明确输入和期望，失败信息带上原始输入，便于定位是哪一组规则不成立：

~~~go
func Add(a, b int) int { return a + b }

func TestAdd(t *testing.T) {
	tests := []struct {
		a, b, want int
	}{
		{1, 2, 3},
		{-1, 1, 0},
	}
	for _, tt := range tests {
		if got := Add(tt.a, tt.b); got != tt.want {
			t.Errorf("Add(%d, %d) = %d, want %d", tt.a, tt.b, got, tt.want)
		}
	}
}
~~~

用 go test ./... 运行全部包，用 go test -cover ./... 查看语句覆盖率。覆盖率只说明代码被执行过，不证明断言检查了正确行为。

示例只演示表驱动结构，不表示整数加法需要重复测试标准库。自己的业务更值得覆盖：非法金额报错、未知状态保留、重复请求不再扣库存，以及失败后状态没有部分提交。预期从业务规则或可手算样本得出，不能在测试里复制一份实现公式当作答案。

## 常用检查

~~~console
go fmt ./...
go vet ./...
go test -race ./...
go test -bench=. -benchmem ./...
~~~

go fmt ./... 会对模块中的 Go 包执行格式化；gofmt -w 则应传入 Go 源文件路径，例如 gofmt -w main.go，它本身不会递归遍历目录。竞态检测、静态检查和基准测试解决不同问题，不能互相替代。测试依赖外部服务时，应把快速单元测试与需要 Docker 或数据库的集成测试分开。

Go 还内置 fuzz testing，适合用来探索 JSON、协议解析和边界校验中的异常输入。模糊测试应保持目标函数无外部副作用，并把发现的问题转成固定回归用例。

race观察本次执行触及的并发访问，没报告不等于其他调度路径一定安全；vet寻找一些可静态识别的问题，也不理解全部业务。fuzz可以检查“合法输入往返后不变”“任意输入不崩溃”等性质，但性质本身要有意义，不能把解析失败一律忽略后宣布通过。

## 快速反馈与真实依赖各留位置

纯金额或状态函数适合单元测试，HTTP使用httptest验证状态码与请求解析，数据库约束与事务则要在真实数据库中测试。内存替身能验证调用方分支，不能证明MySQL锁或唯一约束行为；外部服务测试独立配置，避免普通单测意外连接生产环境。

基准回答每次操作成本，要记录规模、分配数与重复结果。只看一次ns/op的小差异，无法证明实际接口更快；真正的服务延迟还包括网络、排队、连接池和数据库。先用测试固定正确性，再比较性能，避免把少做了必要工作误当收益。
