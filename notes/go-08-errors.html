Go 08：错误处理：让失败沿调用链说清楚

Go语言与工具链

目录

  • panic 的边界

查订单可能得到三种结果：找到订单，没有这张订单，数据库连不上。后两种都能用error表达，下一步却不同。底层若都返回空对象和nil，上层已经无法恢复这份区别。

错误是普通返回值#

Go 常用“结果 + error”表达失败。调用者应检查错误，并决定是返回、转换为业务错误，还是在边界记录并回复客户端。

error是提供 Error() string 的小接口。文字用于阅读，稳定判断依靠错误身份或类型。检查文字里有没有“not found”，会被包装前缀、语言和驱动版本影响。

go
func loadOrder(id int64) error {
	if id <= 0 {
		return fmt.Errorf("load order: invalid id %d", id)
	}
	return nil
}

需要判断错误类别时，可用自定义错误类型、哨兵错误和 errors.Is / errors.As，不要依靠字符串包含判断。

哨兵错误适合稳定类别，例如 ErrOrderNotFound；自定义类型适合携带字段和限额。%w 包装保留原因，Is沿错误链判断类别，As寻找相应类型；%v 只拼文字，会丢掉这类关系。

go
if errors.Is(err, sql.ErrNoRows) {
	// 转换为业务上的“订单不存在”
}

panic 的边界#

存储层可以把sql.ErrNoRows转成订单包自己的不存在错误，避免业务绑定驱动；连接失败则保留原因并补充查询上下文。HTTP边界把不存在映射为404，把系统故障映射为约定的5xx，内部SQL和连接串留在受控排查范围。

公开底层错误也会建立依赖。调用方一旦使用Is识别某个驱动错误，替换驱动就可能影响它。只公开确实需要区分的类别，其余原因用于排查。

panic 用于不可继续执行的程序错误或初始化失败等少数场景，不应代替普通校验和业务错误。recover 只能在同一 goroutine 的 deferred 函数中捕获 panic；HTTP 框架的恢复中间件只能保护请求 goroutine，不能自动保护你另外启动的后台 goroutine。

恢复中间件无法自动回滚已经发送的消息或外部付款。库存不足、无效输入与远程超时属于可预期失败，正常错误路径更容易验证。捕获以后仍要确认失败没有被当作成功提交。

保留错误原因，也避免重复记录#

  • 错误包装时保留原错误：fmt.Errorf("query order: %w", err)。
  • 不要重复记录同一错误并制造多条相同日志；在拥有足够请求上下文的边界记录。
  • 不要吞掉错误后返回成功空值。

同一个数据库错误若在仓储、服务、Handler各记一次，看起来像三次失败。通常底层补上下文并返回，在掌握请求标识与操作信息的边界记录一次。某层真正执行重试或补偿时，再记录它独有的处理结果。

超时也不能证明远端没执行。创建订单是否可重试，必须结合幂等键与操作状态决定；error提供失败信号，不负责推导重复执行的业务后果。

动手验证#

定义“订单不存在”错误，在存储层包装错误，在 HTTP 边界用 errors.Is 将其映射为 404。
