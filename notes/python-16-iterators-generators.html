Python 16：迭代器与生成器：数据不必一次准备好

有一个计算结果，可以放进 for 循环，打印出来也完全正确。过一会儿再遍历一次，却什么都没有输出。这并不一定是数据丢失，可能是手里的对象已经被消费完了。

先看普通列表与它的迭代器：

python
values = [10, 20]
iterator = iter(values)
print(next(iterator))  # 10
print(next(iterator))  # 20
print(next(iterator, "结束"))  # 结束
print(list(iterator))          # []
print(list(values))            # [10, 20]

可迭代对象能提供迭代器，iter(values) 就执行这一步。迭代器保存当前遍历进度，next 取得下一项并向前推进；耗尽时通常抛出 StopIteration，这里提供默认值后改为返回“结束”。

for 先取得迭代器，再重复获取下一项，直到遇到结束信号。列表可以重新提供一个从头开始的迭代器，刚才那个已经耗尽的迭代器却不会自己复位。因此“能用于for”与“能重复遍历”是不同的能力。

yield 让函数停在产生结果的位置#

如果只需要逐个得到平方，没有必要先建立完整结果列表：

python
def squares(limit):
    for number in range(limit):
        yield number * number


for value in squares(4):
    print(value)

带有 yield 的函数是生成器函数。调用 squares(4) 时会得到生成器对象，函数体还没有把所有平方都算完。第一次获取值，执行到 yield 0 后暂停；下一次继续上次的位置，推进循环，再产生1。局部变量和执行位置随生成器一起保留。

最后得到0、1、4、9。调用一个新的 squares(4) 会创建新的生成器，而不是让旧对象倒回去。生成器也是迭代器，因此具有同样的一次性消费特征。

生成器耗尽后不会自动重放#

python
numbers = squares(4)
print(sum(numbers))   # 14
print(list(numbers))  # []

sum 已经逐个取完所有值，第二次没有剩余内容。把生成器交给两个处理步骤时，必须先决定它们是否可以共用同一次消费。

结果规模不大、确实要重复访问，可以在第一次消费前使用 list(squares(4)) 保存下来。输入可以重新读取，则分别创建生成器也行；但这意味着重复计算或重复I/O，不能假定没有成本。面对无法重放的网络流，就需要明确怎样分发或保存数据。

这也是函数参数值得写清楚的地方。一个只接受单次可迭代输入的函数，若先用 any 检查，再遍历“同一份”数据，前面那一步可能已经消耗了一部分内容。

数据流水处理为什么适合生成器#

读取日志时，可以一边读，一边清理，一边检查，不必让每一步都保存一份完整列表：

python
def cleaned_lines(lines):
    for line in lines:
        line = line.strip()
        if line:
            yield line

lines = [" first \n", "\n", " second\n"]
for line in cleaned_lines(lines):
    print(line)  # 依次输出 first、second

调用者只消费前几项，后面的输入就不会被这段生成器继续处理。这个特点适合大文件、分页读取和逐步产生结果的操作，能够减少等待全部结果完成的时间，也通常降低中间数据的内存占用。

不过，生成器不保证总内存一定小。局部变量若持有一个巨大列表，它仍然存在；下游一旦 list(...) 收集全部结果，也会重新承担整份结果的存储成本。它节省的是不必要的预先物化，不能替代对整个数据流的检查。

延迟执行也会延迟报错和关闭资源#

函数创建生成器时没有真正读取数据，读取错误可能直到遍历时才抛出。因此捕获错误的位置应覆盖消费过程，而不只是创建生成器的那一行。

如果生成器内部打开一个文件，调用者取一项就停止，文件也可能随着暂停的生成器继续保持打开。更清楚的方式是让外层持有资源，再把已打开的文件对象交给清理逻辑：

python
from io import StringIO

with StringIO(" a \n\n b \n") as source:
    for line in cleaned_lines(source):
        print(line)

这里资源的生命周期由外层 with 明确控制。真实文件也可以按相同方式组织。若接口必须返回内部持有资源的生成器，就需要另外约定关闭方式和提前结束时的清理责任。

生成器适合“下一项才是眼下需要的东西”。需要随机访问、按下标修改或反复扫描时，列表可能更合适。两者没有谁全面替代谁，关键在于调用者要怎样消费结果。#
