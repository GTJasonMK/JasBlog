对象新增一个字段，可选版本、只读版本和返回类型都跟着手改，容易漏一处。类型变换可以从原声明生成相关视图，但前提是业务关系真的一致；如果更新输入只允许两个字段，不能因为变换方便就开放整张表。

映射类型遍历键并生成新属性；条件类型根据类型关系选择结果。infer 可在条件类型中提取内部类型。它们是工具类型和库声明的重要基础。

~~~ts
type Optional<T> = {
  [K in keyof T]?: T[K];
};

type ElementOf<T> = T extends readonly (infer Item)[] ? Item : T;
~~~

先使用内置工具类型；只有类型逻辑重复且能明显提升表达力时，才编写自定义类型工具。

Optional先用keyof枚举T的键，K依次代表每个键，T[K]取得原字段类型，问号把输出字段改成可选。它与常用Partial表达相近意图，实际项目直接用内置工具通常更清楚。这只产生类型，不生成删除字段或复制对象的函数。

ElementOf检查T是否能匹配只读数组形式，能匹配就通过infer取元素类型，否则保留T。传number[]得到number，传string得到string，传只读任务数组得到任务类型。infer是类型匹配中的占位推导，不在运行时取数组第一项。

## 联合是分别判断，还是整体判断

条件左边直接使用类型参数T时，常会对联合成员分别判断。ElementOf<string[] | number>得到string或number，先处理数组成员，再处理数值成员；不是把整个联合当作一个不可拆对象一次决定。

如果确实要整体判断，可以把条件两边放进元组形式，例如 `[T] extends [readonly unknown[]]`。这会改变含义，并非通用优化。先用数组、非数组、联合与never等小输入确认结果，再决定需要哪一种行为。

映射修饰符还能增加或移除readonly与可选标记，键重映射可以生成新键。但工具越复杂，调用方越难读错误信息；不能为了少写两行普通类型，制造需要多层展开才能解释的公共合同。

## 复杂类型也需要小例子验证

- 类型体操难以阅读时，应回到简单对象和函数边界。
- 联合类型上的条件类型可能分发到每个成员，结果与整体判断不同。
- 复杂类型应配小例子验证推导结果。

类型验证用编译器实际接受与拒绝的赋值检查，不靠“编辑器看起来像对了”。运行时行为则另写行为测试；一个字段变成readonly，不意味着传入对象已经深冻结，Schema与对象生命周期仍各自负责。

## 动手验证

实现一个类型工具，将对象的所有字段变成只读；再用编辑器检查推导结果。
