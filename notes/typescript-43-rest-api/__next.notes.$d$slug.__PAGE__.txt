修改任务时只想改变状态，没有提供标题。如果后端把输入缺失字段也写成空值，局部更新就变成了数据清除。接口设计除了路径和方法，还要说明省略、null与合法字段各代表什么。

URL 表示资源，HTTP 方法表示操作。用集合路径获取或创建资源，用资源 id 访问、修改或删除单条记录。PATCH 通常用于局部更新，响应状态与内容要保持一致。

列表 API 可用 limit、cursor 等分页参数；服务端需设置上限并校验输入。创建成功返回 201 和新资源；删除成功可返回 204。

错误响应应有稳定结构，例如 code 与 message；内部堆栈只进入服务端日志。

GET /api/tasks返回当前用户的一页任务，POST创建并返回201；GET /api/tasks/:id读取一项，PATCH只改变实际提供的白名单字段，DELETE成功可以返回204。204没有正文，客户端不再要求解析任务对象。

PATCH空对象可以明确拒绝，title的null若不允许清空则返回输入错误。客户端不能传ownerId转移归属，也不能自行指定生成编号和创建时间。字段是否可修改来自业务规则，不从数据库模型自动复制。

## 列表不是无限数组

limit解析为有范围的整数，排序使用固定字段与编号次序，cursor对应这份排序继续读取。按创建时间相同的记录必须有稳定并列规则，否则翻页可能重复或漏项。offset简单但深页可能增加扫描，按实际规模选择。

列表响应说明当前结果、下一页游标与是否还有内容，不让客户端靠“返回条数少于某值”猜全部语义。筛选也参与缓存身份，权限范围始终由当前服务端会话决定。

## 资源归属和查询范围由服务端限定

- 不把所有操作都设计成 POST。
- 不相信客户端传来的 ownerId；身份来自服务端会话。
- 分页参数不能允许无限制数据库扫描。

不存在与无权访问可统一404避免暴露资源是否存在，未认证仍按合同401。状态冲突、字段错误与系统故障分别映射稳定code，让客户端知道纠正输入、重试或重新确认会话。创建超时是否重试，还要按幂等或状态查询合同处理。
