Python 21：虚拟环境与项目结构：让依赖跟着项目走

项目A还依赖某个库的旧接口，项目B却要用它的新版本。把所有包都装到系统同一个目录，升级B时就可能让A无法运行。虚拟环境让项目拥有各自的包安装目录，把这类冲突隔开。

不过，隔离只是第一步。把环境删掉，另一个人还能不能重建同样的项目，取决于我们有没有记录解释器和依赖要求。一个正在运行的 .venv 目录，不等于一份可重复使用的项目说明。

创建环境用的是哪个Python#

venv 属于标准库，调用它的解释器决定了环境所基于的Python版本。创建和安装可以这样开始：

console
python -m venv .venv
# macOS/Linux
source .venv/bin/activate
# Windows PowerShell
.venv\Scripts\Activate.ps1
python -m pip install httpx

上面激活命令按操作系统选择，不是两行都执行。激活主要调整当前终端的路径查找顺序，不会强制编辑器、Notebook和另一个终端也使用这个环境。用 python -c "import sys; print(sys.executable)" 可以核对实际解释器。

安装工具 pip 独立维护，常由Python发行版提供，或通过 ensurepip 引导安装，它本身不应与标准库模块混为一谈。python -m pip 让安装操作跟着当前解释器，比一个来源不明的裸 pip 命令更容易核查。

需要给其他工具调用时，也可以直接使用 .venv/bin/python 或Windows环境中的解释器路径，无需依赖激活。环境损坏或项目切换版本时，通常从声明重新创建，不把某台机器上的整个环境目录搬来搬去。

隔离了，还要记录什么#

pyproject.toml 是项目元数据与工具配置的统一入口，可以声明项目名称、最低Python版本和直接依赖。它说的是项目需要什么，具体怎样解析和锁定依赖，由所选工具负责。

假设项目允许 httpx>=0.27,<1，这表达一个兼容范围。今天和下个月安装时，工具可能选择范围内不同的版本。应用若要求部署环境可重复，应记录经过验证的完整依赖集合或使用相应锁文件，构建时按它安装。

pip freeze 可以列出当前环境中的包，但它也可能带上临时调试工具、偶然安装的包和本机路径。它可以帮助记录环境，不能自动替你确定哪些才是项目的真实依赖。公共库的兼容范围与应用部署的精确版本，也有不同用途。

除了Python包，程序若依赖系统命令、数据库客户端或原生库，这些条件同样要写进项目说明。锁住Python包并不等于所有机器环境都已经一致。

目录结构让源码与运行环境各自归位#

一个需要安装、测试并交付的项目可以采用：

text
my_project/
├── pyproject.toml
├── src/my_project/
├── tests/
└── README.md

src/my_project 放可导入代码，tests 放行为检查，README 交代启动与配置，.venv 则是本机生成的运行环境。它们用途不同，不应把依赖源码、生成报告和业务模块都堆进同一层。

src 布局的一个好处是让测试更接近安装后的导入方式，减少“当前目录里碰巧有源码，所以没发现打包漏文件”的情况。相应代价是需要先安装项目，例如在开发环境使用 python -m pip install -e .；完整可安装配置见项目打包。

只有一个小脚本时，不必提前创建一套很复杂的目录。但一旦出现可复用模块、测试和交付入口，就值得让它们有明确归属。

从干净环境验证一次，才能知道依赖有没有写全#

在新的临时环境中按项目声明安装，再从源码目录之外导入并运行，是检查依赖遗漏的直接方法。若旧环境能用、新环境不能用，先核对缺少的是已忘记声明的包、错误的解释器版本，还是依赖系统组件。

虚拟环境目录、缓存和本机凭证不进入Git；项目元数据、选定工具的锁文件和可公开配置模板则应随代码保存。这样拿到仓库的人重建的是一个有依据的环境，而不需要猜作者机器上装过哪些东西。
