Go 29：限时促销项目：先确定接口与订单状态

Go促销订单项目

目录

  • 功能范围
  • REST 接口
  • 数据与状态
  • 动手验证

取消与支付同时到达，两个请求都读到待支付，随后各自修改，后一次覆盖前一次。接口各自跑通，订单却没有稳定含义。开始项目之前，先把允许的转换与只能发生一次的结果写清楚。

功能范围#

项目提供用户登录、商品查询、促销活动查询、参与抢购、订单查询、模拟支付和通知。初版是模块化单体，用户、商品、促销、库存和订单各有清楚的包边界；之后再演示拆分服务。

这些是逐步实现的学习范围，不是本篇已经交付的商城。先完成普通下单与查询，再引入异步削峰；登录和支付保留明确的本地演示边界，不将模拟接口当作真实资金入口。

REST 接口#

方法与路径用途
POST /api/v1/auth/login登录并取得演示用访问令牌
GET /api/v1/products/{id}查询商品
GET /api/v1/campaigns/{id}查询促销活动
POST /api/v1/campaigns/{id}/claims参与抢购；要求认证与幂等键
GET /api/v1/orders/{id}查询当前用户自己的订单
POST /api/v1/payments/mock-callback模拟支付回调，仅用于本地练习
GET /healthz、GET /readyz存活检查与依赖就绪检查

用户 ID 应从认证身份中取得，不能相信客户端传入的 user_id。订单查询必须检查资源归属。

claims在同步版本可以返回已创建订单，在异步版本返回202与受理编号。订单尚未生成时，也必须能查询受理状态，不能因为订单表没有记录就把已接受请求当作不存在。切换协议要同时调整状态与客户端行为。

数据与状态#

核心表包括 users、products、campaigns、inventory、orders、order_items 和 idempotency_records。订单状态建议显式定义为 pending_payment、paid、cancelled；所有状态迁移都通过业务函数校验，不能让客户端任意传目标状态。

待支付可以支付或取消，已支付不能被迟到的失败回调改回待支付。取消以后收到真实支付成功，需要对账与退款流程，不能丢弃资金事实；学习版则明确拒绝模拟非法转换。

并发更新还要带预期旧状态，并检查受影响行数。函数里先判断、后无条件写入，仍有竞争窗口。唯一约束也要对应具体业务：用户与幂等键限制同一次请求，活动与用户限制参与次数，支付流水号限制重复入账，不能混成一项笼统的“防重复”。

验收准备成功、库存不足、重复提交、越权查询和竞争状态转换。各自证明一条规则，只有成功路径不足以验证这套设计。

动手验证#

画出接口和表的关系图，写出订单状态转换表，并标记哪些写操作需要唯一约束或幂等键。
