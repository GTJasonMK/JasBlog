`n++` 看起来是一件事，实际上包含读取旧值、计算新值和写回。两个goroutine可能都读到0，再分别写回1，最后只增加一次。问题不在于加法，而在于这一组操作没有作为受保护的整体执行。

## 同步状态

多个 goroutine 访问同一可变数据时，要么用锁保护，要么改为单所有者通过 channel 处理。互斥锁保护的是一段临界区，不是整个程序。一次性初始化可用 sync.Once；简单计数或状态可评估 sync/atomic，但复合状态通常仍需要锁。原子操作不能自动让多步业务更新成为一个整体。

~~~go
type SafeCounter struct {
	mu sync.Mutex
	n  int
}

func (c *SafeCounter) Add() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}
~~~

两个方法使用同一把锁，读取也受到保护。若Add加锁而Value直接返回n，仍然可能发生数据竞争。锁保护某个状态的不变量，访问这份状态的全部路径都要遵守相同规则；带Mutex的结构体也不应在使用后复制。

用锁时尽量缩短临界区；不要持锁执行网络请求或等待不确定时长的操作。读多写少场景可以评估 RWMutex，但应先测量再优化。

若不变量是“库存减少的同时预留数增加”，只把两个字段分别换成原子整数还不够，观察者仍可能看到中间状态。需要共同锁、单所有者消息循环，或者外部存储事务，让整个规则成立。RWMutex也不是读多就必然更快，它有额外开销与调度行为。

## context 传播

context.Context 通常作为函数第一个参数。下游 HTTP、数据库或后台任务应使用调用者传入的 context，以便请求取消时停止工作。创建 WithTimeout 后要调用 cancel，释放计时器等资源。

~~~go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()
result, err := repository.Find(ctx, id)
~~~

不要把 context 长期存到结构体，也不要把业务参数塞进 context。取消信号是协作式的，代码必须检查 Done 或调用支持 context 的 API。

超时后context的Done关闭，Err返回截止时间或取消原因；它不会强行终止一个忽略信号的函数。HTTP调用要用带context的请求，数据库要用QueryContext等相应接口，CPU循环则要在合适位置检查取消。每层另起Background会切断调用方的取消链。

`cancel` 即使在操作提前成功后也要调用，以释放当前派生context的资源；它不代表业务失败。请求取消后，不能继续用这个context执行必须完成的持久化补偿，应交给有独立生命周期和明确超时的任务机制，而不是偷偷让请求goroutine无限运行。

## 竞态检查

运行 go test -race ./... 可发现许多数据竞争，但它只能检查被测试运行路径实际触及的代码。

可以并发启动100个Add，等全部完成后断言Value为100，再在race下执行。取消测试则让worker在等待输入时取消context，用结束信号确认它退出，不能只睡一会儿就假定没有泄漏。一个测试检查状态同步，另一个检查生命周期，它们互不替代。

## 动手验证

给一个需要循环处理任务的 worker 加入 context 取消。取消后等待 worker 退出，确认不会遗留 goroutine。
