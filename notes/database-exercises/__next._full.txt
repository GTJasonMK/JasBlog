看过正确SQL以后觉得能懂，与独立写出并解释结果之间还有一步。练习先给一个可核对的问题，要求保存输入、顺序与输出；答案不同的时候，能沿过程找出哪项判断出了偏差。

可以先独立完成，再看[参考答案](/notes/database-exercise-answers)。每题保留 SQL 或操作顺序、预期、实际输出和解释。

## 阶段一：基础、建模与 SQL

前置：第 1 至 6 章，尚未提交修改种子数据。

这一阶段先固定行粒度。零库存、每日金额与客户汇总各回答不同问题，连接后多一行就可能让总额改变；先手算种子，再核对SQL，不用去重凑答案。

| 题号 | 任务 | 验收要求 |
|---|---|---|
| E01 | 报告数据库、身份、版本、时区和隔离级别 | 以 SQL 输出为依据，解释默认自动提交 |
| E02 | 为客户联系人与多仓库库存建模 | 明确主键、外键、唯一性、必填与数量约束 |
| E03 | 查零库存商品与 1 月 10 日 UTC 的订单 | 商品为 id 3，订单为 id 1、2；使用半开时间区间 |
| E04 | 列出所有客户的订单数、总金额 | 包括无订单客户，金额单位明确 |
| E05 | 找无订单客户，算已支付且存在成功支付的订单总额 | 客户 id 3；金额 59700 分；不重复计算 |
| E06 | 比较错误支付关联求和与正确求和 | 解释 99500 分怎样产生，不能用 `SUM(DISTINCT 金额)` 补救 |
| E07 | 求每位客户最新订单与客户内累计金额 | 最新订单为客户 1 的订单 2、客户 2 的订单 3；处理同时间排序 |
| E08 | 给 1 月 9 至 12 日每日已支付订单额补零 | 四行依次 0、39800、19900、0 分；按 UTC |

通过条件：八题结果正确，并能解释每个关联的结果粒度。语句能运行但金额错，不进入下一阶段。

## 阶段二：事务与应用边界

前置：第 7 至 10 章，安装下单函数。

并发题把顺序当输入的一部分。两个连接分别何时读、写与提交，决定看到的版本与等待；正常顺次调用没有问题，尚不能证明同一时刻竞争也成立。

| 题号 | 任务 | 验收要求 |
|---|---|---|
| E09 | 双会话复现 RC 与 RR 的读取差异 | 保存执行顺序与两次读取结果 |
| E10 | 在 RR 下复现值班写偏斜，再换 Serializable | 展示跨行规则破坏与 `40001`，说明完整重试 |
| E11 | 复现阻塞与死锁 | 找出阻塞 PID；获取 `40P01`；最终回滚 |
| E12 | 验证正常下单、重复请求、换内容复用键、缺货、零数量、空参数 | 自检通过，失败不残留业务记录 |
| E13 | 两会话竞争同请求，再竞争只够一单的库存 | 同键仅一单；不同键只有一个成功；账与库存相符 |
| E14 | 分析提交时断网与连接池预算 | 解释结果未知、原键确认、重试边界与总连接数 |

E13 用自己新建的客户和库存为 1 的测试商品，初始库存同时写 `opening` 流水，不修改种子商品。保存夹具 id，不依赖序列连续。

通过条件：没有负库存、重复订单、重复扣减、失败残留或未说明的超时状态。只能展示顺序调用不足以通过并发题。

## 阶段三：性能与维护

前置：第 11 至 13 章。

先保持查询结果不变，再比较完成相同工作需要多少扫描、排序和存储。机器不同，绝对毫秒数也会不同，重点在计划与工作量能否支撑解释。

| 题号 | 任务 | 验收要求 |
|---|---|---|
| E15 | 执行 L4，分析索引前后的同一查询 | 20 万行、前后计划、扫描量、块数、至少五次时间测量 |
| E16 | 为客户列表、待发送事件、商品订单查询选索引 | 检查已有索引，说明键顺序、写入代价与覆盖限制 |
| E17 | 观察更新、VACUUM、长事务与大小 | 区分可复用空间、文件缩小和统计更新 |
| E18 | 建立月分区事件表，对比带与不带分区键的查询 | 解释裁剪与跨分区唯一性限制 |

通过条件：不靠强制优化器开关制造结论，不把三行小表或一次缓存差异当成性能证据。

## 阶段四：安全、恢复、运维与发布

前置：第 14 至 20 章。

权限要同时证明允许与拒绝，恢复要真正还原到独立目标，变更要保存中断进度与原值。这里的完成标准跟数据结果走，文件存在或命令返回成功只证明其中一段。

| 题号 | 任务 | 验收要求 |
|---|---|---|
| E19 | 建立只读组与真实登录用户 | 读取成功；写入、原始邮箱和建表被拒绝；凭据不入文档 |
| E20 | 把逻辑备份恢复到新库 | 目录可读、无恢复错误、业务核对、实际耗时 |
| E21 | 完成 L7，恢复误删前数据 | 源库标记为 1、3；恢复库为 1、2；目标暂停状态与日志 |
| E22 | 给异步复制和跨区容灾制定承诺 | 说明 RPO/RTO 证据、同步条件、防双主与旧主回归 |
| E23 | 排查 WAL 增长、复制延迟与连接耗尽 | 每种现象至少给一个可排除的假设和对应查询 |
| E24 | 制定容量与告警方案 | 预算包含索引、WAL、备份、临时文件和重写空间 |
| E25 | 完成新增必填字段与分批回填 | 可中断续跑，非法值失败，验证历史数据，DDL 有等待上限 |
| E26 | 提交一次故障复盘与一次数据变更单 | 有范围、因果证据、预期行数、恢复依据和业务确认 |

通过条件：实际完成 E20、E21。备份生成成功但未恢复不能通过；同机恢复不宣称通过异地容灾。

## 阶段五：迁移方法与交付

前置：第 21 至 23 章。

迁到另一个系统时，先找原来依靠的约束与故障语义，再逐项验证。选型不要求组件多，能说明现有系统已经满足目标，也是一份有依据的结论。

| 题号 | 任务 | 验收要求 |
|---|---|---|
| E27 | 在独立 MySQL 8.4 环境复现范围锁与恢复 | 保存版本、隔离设置、锁等待、独立恢复结果；未运行就标未完成 |
| E28 | 写出 PG 与 MySQL 的五项业务相关差异 | 至少包含隔离、存储、日志、DDL、索引限制 |
| E29 | 设计重复取消订单与支付回调去重 | 明确状态条件、流水唯一性、事务与重复请求行为，不调用真实支付 |
| E30 | 写一页缓存、分析副本与分片选型说明 | 每项给触发测量、事实来源、数据延迟、失败与恢复责任 |
| E31 | 为示例订单库比较两个关系型数据库候选 | 分别写优点、代价、五个兼容验证点和选择依据，不用品牌排名代替证据 |
| E32 | 分析四个产品承诺的实际边界 | 解释 Redis 持久化、MongoDB 事务、TiDB 的 MySQL 兼容，以及 OpenSearch 与 Elasticsearch 的迁移要求 |
| E33 | 为订单、搜索、销售报表设计最小数据架构 | 说明事实来源、允许延迟、删除传播、恢复方式和增加组件的触发条件 |

随后按[综合项目](/notes/database-order-project)交付。可记录 PostgreSQL 主线通过、MySQL 尚未完成，不能将二者合并为全部通过。

题目之间有重复机制，但证据范围各不相同。保留失败与尚未运行的项目，下一次直接补对应条件，不需要为了进度表好看重新改写观察结果。
