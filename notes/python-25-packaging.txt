项目在自己的源码目录能运行，换一台机器却导入失败，常常是因为“源码刚好在当前路径”掩盖了安装问题。打包要明确告诉工具：项目叫什么、依赖哪些东西、哪些文件属于它，安装以后怎样找到入口。

这不是每个临时脚本都需要做的事情。代码要被其他项目导入、通过命令行长期使用，或作为版本化产物部署时，可安装的包才让交付边界更清楚。

## 先准备一个确实可以安装的结构

沿用[项目结构](/notes/python-21-environments-projects)中的 `src` 布局：

```text
example-tools/
  pyproject.toml
  src/
    my_project/
      __init__.py
      cli.py
```

`__init__.py` 可以先留空，`cli.py` 提供一个没有外部服务依赖的命令：

```python
# src/my_project/cli.py
def main():
    print("工具已运行")
```

在项目根目录添加 `pyproject.toml`：

```toml
[build-system]
requires = ["setuptools>=64"]
build-backend = "setuptools.build_meta"

[project]
name = "example-tools"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

[project.scripts]
example-tools = "my_project.cli:main"

[tool.setuptools.packages.find]
where = ["src"]
```

`[build-system]` 声明构建后端及构建时需要的工具，这里选择Setuptools。`[project]` 描述交付项目本身的名称、版本、解释器范围和运行依赖。构建依赖与运行依赖用途不同，不应因为本机装过构建工具，就把它写成使用者运行时必需的依赖。

`where = ["src"]` 让后端从 `src` 发现包。`[project.scripts]` 声明安装后生成的命令，入口写成“可导入模块:可调用对象”。工具启动时会导入模块并调用 `main`，所以模块本身也应避免导入即启动交互等副作用。

这里的发行项目名是 `example-tools`，导入包名是 `my_project`。两者可以不同，安装时用前者，`import` 时用后者。它们不是靠把连字符改成下划线自动对应的，而由实际包目录和配置决定。

## 开发安装方便修改，但不是最终产物

进入项目根目录，在当前虚拟环境中执行：

```console
python -m pip install -e .
```

可编辑安装把环境与开发源码关联，修改普通Python代码后通常不需要再复制安装。更改入口、项目元数据或包发现规则时，可能仍需要重新安装。它适合本地开发，不代表已经检查了最终安装包里到底放进哪些文件。

接着执行 `example-tools`，应看到“工具已运行”。也可以运行 `python -c "from my_project.cli import main; main()"` 验证导入。命令名称和Python模块是两个入口，都应符合这份配置的承诺。

## 构建一次，再从源码目录之外安装

用于正式分发的常见产物有源代码分发包和wheel。前者供构建使用，后者是可以直接安装的构建产物；包含原生扩展的wheel还可能与平台、架构和Python实现有关。可以通过构建前端运行后端：

```console
python -m pip install build
python -m build
```

产物通常进入 `dist`。在另一个干净虚拟环境中安装生成的wheel，再切换到项目目录之外运行入口，就能检查是否真正依靠安装产物，而不是依靠当前目录里遗漏打包的源码。

这里可以得到类似 `example_tools-0.1.0-py3-none-any.whl` 的文件名。文件名中的规范化不改变实际导入名；应安装实际生成的文件，不要凭项目显示名猜路径。

如果包里还需要模板、静态数据或其他资源文件，也要检查它们是否包含在产物中。编辑模式能读到源码旁边的文件，不代表wheel已经携带了它们。不同构建后端有各自配置规则，实际项目按所选后端的文档声明并验证。

## 版本要求需要真实验证

`requires-python = ">=3.12"` 让安装工具提前判断解释器是否支持，但它只是声明，不能证明代码确实兼容所有满足条件的版本。最低支持版本需要实际测试；某个依赖有额外限制时，项目的兼容范围也要一起检查。

准备公开上传还需核对包名、许可、说明文档及产物中没有本机凭证。示例项目在本地构建安装即可验证打包流程，不应随意把教程占位名称发布到包索引。正式分发步骤可查[PyPA打包指南](https://packaging.python.org/en/latest/tutorials/packaging-projects/)。
