Go 24：GORM 的作用与持久层的边界

把SQL改写成链式API以后，最容易产生的错觉是事务、校验与索引也由ORM一起处理了。实际上 Where 最终仍然形成SQL条件，更新范围与事务连接仍然决定结果。ORM减少的是一部分映射重复，不会改变数据库的并发规则。

使用 ORM 的边界#

GORM 可减少常见映射代码，适合普通增删改查。开发者仍要理解 SQL、索引、锁和事务。热点路径可使用明确的参数化 SQL，但不要把业务规则复制到多个访问路径。

下面是已有模型与错误定义下的事务片段，productID与正quantity已在调用前验证。库存与订单都使用回调提供的tx：

go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	result := tx.Model(&Inventory{}).
		Where("product_id = ? AND available >= ?", productID, quantity).
		Update("available", gorm.Expr("available - ?", quantity))
	if result.Error != nil {
		return result.Error
	}
	if result.RowsAffected != 1 {
		return ErrInsufficientStock
	}
	return tx.Create(&order).Error
})

真实代码应为数据库设置连接池和超时，所有查询带调用者 context。利用 SQL 日志或 DryRun 等能力检查生成语句，注意日志中的敏感参数处理。

在进入事务前先校验 quantity > 0，并为 product_id 建立唯一索引；不能仅依赖 RowsAffected == 1 来弥补无效数量或重复库存行。

回调返回error时回滚，返回nil才尝试提交；外层err还包含提交阶段的失败。因此必须检查Transaction的最终返回值。若把 tx.Create 写成 db.Create，订单可能在回调事务之外提交，后续回滚也无法撤销它。

gorm.Expr 把扣减表达式交给数据库计算，避免先读到Go再写回旧值。参数仍用占位符，表达式字符串由程序固定。RowsAffected检查来自唯一库存行这一前提；无约束的多行数据不能靠一个期望值变成正确模型。

更新false时有没有真的发出SQL#

GORM部分基于结构体的Updates操作默认忽略零值，可能跳过false、0或空字符串。局部更新需要明确选择字段，或使用包含目标字段的map，并区分省略与清空。不要看到返回nil就认为每个字段都被按请求修改。

读取关联也要检查生成语句数量。循环逐个查订单明细会形成N+1查询，数据量小的时候不明显，列表一大就增加往返。预加载或明确连接可减少往返，但仍要控制页大小与返回列，不把整个关系图无界读进内存。

迁移#

教学项目可以使用版本化迁移脚本。自动迁移适合受控的本地演示，但生产结构变更应审查增删列、索引锁表和兼容发布顺序。数据库迁移失败要让部署显性失败。

持久层测试要真正制造订单插入失败，检查事务后库存是否恢复，再检查取消、重复请求和零值更新。只用返回nil的仓储替身，能够验证服务调用顺序，却证明不了ORM生成的SQL、约束或回滚行为。
