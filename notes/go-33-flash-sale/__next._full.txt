瞬间请求超过数据库稳定写入能力，可以先受理再逐步创建订单。但排队没有让数据库更快，只是把一部分等待挪到后台；队列长度、可等待时间与受理承诺都必须有上限。否则接口看起来很快，用户却一直等不到结果。

## 处理流程

1. 验证登录身份、活动时间、数量范围和限购规则。
2. 调用 Redis Lua，在同一原子操作中检查用户参与记录和幂等键、预留活动库存、写入预留记录，并将事件追加到 Redis Stream。
3. 后台 relay 通过 Stream 消费组读取待发布事件，发送到 Kafka；收到 Kafka 确认后再用 XACK 确认该消费组已处理。XACK 只把消息从该组的 pending 列表移除，不会删除 Stream 中的消息。需要恢复被消费者取出但未确认的事件，并限制 Stream 保留策略，避免积压时事件被提前删除；不能用固定长度裁剪盲目删除尚未处理的事件。积压达到容量水位时，应在入口限流或拒绝新请求，而不是无限接受后持续消耗内存。
4. Kafka 消费者以幂等方式创建订单，并记录状态。
5. 入口在完成可靠受理后返回202与request_id，不等待后台步骤全部完成；客户端先按该标识查询受理状态，订单生成后再关联order_id。

不能在入口返回“订单已创建”，除非订单确实已持久化。更准确的响应是 HTTP 202 Accepted（请求已受理），并提供可查询的业务标识。Redis 预留成功后，MySQL 订单表还应有 (campaign_id, user_id) 等业务唯一约束，防止 Redis 数据丢失、恢复或重放时创建重复订单。幂等键唯一约束也应绑定用户和请求内容，避免同一用户用同一 key 重放不同请求。

这里还假定活动每用户只允许一张订单，才使用活动与用户唯一；允许多次购买时，应改成明确的限购计数与请求规则，不能保留这个约束又宣称支持任意次数。普通下单与抢购应复用相同订单不变量，同时明确库存预留与最终库存结算的分工，避免各扣一次。

受理状态至少能区分处理中、已生成订单与确定失败。Redis记录过期而MySQL尚无订单，不能直接告诉用户下单失败，因为消息可能还在重试；需要根据事件与预留状态对账。每个状态有持有者和完成条件，超时只是启动检查，不自动证明业务未发生。

## 双写失败

Redis 预留和 Kafka 发布无法组成一个原子事务。Kafka 确认前不能对 Stream 消息执行 XACK；relay 超时或在 Kafka 确认后、XACK 前崩溃，都可能导致同一事件再次发送，因此要复用固定 event_id 并让消费者幂等。Redis Stream 的持久化、复制和保留策略必须覆盖预期故障窗口，积压和 pending 消息要有监控与回收机制。不能在“发送失败”后立刻释放库存；若确认事件未被接受，再按预留记录幂等补偿。消费者写库失败时，消息要有限重试；永久失败进入死信与人工处理。

Redis 库存与 MySQL 库存不是一个事务。预留数据的持久化策略、故障切换数据丢失窗口、待发布事件恢复、定期对账、过期预留释放和异常告警都要纳入设计；不要声称 Lua 能保证跨 Redis、Kafka、MySQL 的全局原子性。Lua 的命令序列对其他客户端不可见为中间态，但发生运行错误时此前成功的写入不会自动回滚。Redis Cluster 多 key Lua 还要求脚本涉及的 key 同属一个 hash slot。

补偿必须按预留身份与当前状态执行：尚未成交才释放，重复释放不再增加库存，迟到创建不能复活已明确取消的请求。无法确认的状态保留待对账，不能为了立刻显示成功或失败而编造终态。

这套方案增加了Stream与Kafka两段传递，学习时用来观察不同边界。流量与可靠性需求不需要它时，优先保留数据库事务或更短的排队路径；每加一段，都要证明它带来的容量或解耦收益覆盖恢复成本。
