Python 24：调试、日志与配置：留下能解释问题的信息

一份文件有100条记录，报告却只有97条。到最后输出的位置加一句“生成成功”，不能解释少掉的三条去了哪里。更有用的问题是：读取后有多少条，过滤后有多少条，分组后又有多少条？沿处理过程找到数量第一次不符合预期的位置，才能把范围缩到具体步骤。

调试先需要可以重复的输入。保留一份去掉敏感信息的最小样本，确认每次都能出现同样差异，再检查中间状态。还没确定复现条件，就同时修改编码、排序和过滤逻辑，即使结果变对了，也很难知道真正原因。

断点看当前状态，日志保存发生过程#

本地调试时，可以在可疑位置加入 breakpoint()，暂停后查看变量、调用栈，逐步执行。它适合观察一份具体输入怎样走到错误状态。放到无人值守的定时任务里，却可能让程序一直等交互，所以临时断点应在排查结束后移除。

长期运行的程序更需要日志：错误已经发生，人不在现场，也能根据当时记录还原过程。标准日志模块提供级别、输出目标和格式：

python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)
logger = logging.getLogger(__name__)
logger.info("已处理 %d 条记录", 12)

INFO 可以记录任务开始、结束和处理数量，WARNING 表示值得注意但当前仍可处理的情况，ERROR 表示某项操作失败。DEBUG 留给更细的诊断信息。级别的作用是让使用者选择关心的细节，不是把所有内容都标为最高级别。

logger.info("已处理 %d 条记录", count) 把格式和参数分开，消息被级别过滤时可以避免字符串格式化。不过传入的参数表达式仍会先求值，昂贵的调试计算不能因为用了 %s 就认为没有成本。

日志要保留上下文，也要避开敏感信息#

处理失败只记录“读文件失败”，仍然不知道是文件缺失、没有权限还是路径指向目录。可以在异常处理块中使用 logger.exception，保留调用栈：

python
from pathlib import Path

def load_source(path: Path) -> str:
    try:
        return path.read_text(encoding="utf-8")
    except OSError:
        logger.exception("读取输入失败：%s", path.name)
        raise

这里记录文件名，并让原异常继续传播。它不会在失败时返回空文本，因此调用者不会把“读失败”误认为“文件确实没有内容”。项目若已在外层统一记录同一异常，就不必每层都再记一次，避免一件事产生许多重复错误日志。

对100条变97条的问题，日志应记录输入数量、过滤条件和每个阶段的结果数量，需要逐条定位时再使用合适的记录标识。整份用户资料、请求头和凭证不必跟着打出来。诊断需要的信息越明确，越不需要无差别保留所有输入。

多任务同时执行时，还可以带任务ID或请求ID，将属于同一次处理的记录关联起来。日志保存多久、写到哪里和磁盘是否会写满，也要在实际运行环境里管理；单靠终端上能看到输出，不等于有了可靠的长期记录。

配置读进来后，先变成确定的数据#

环境变量提供的是字符串。BATCH_SIZE="100" 要作为批量大小使用，就需要解析并检查范围；缺失值能否采用默认值，也应由配置合同决定：

python
import os

def read_batch_size():
    raw = os.environ.get("BATCH_SIZE", "100")
    try:
        value = int(raw)
    except ValueError as exc:
        raise ValueError("BATCH_SIZE必须是整数") from exc
    if not 1 <= value <= 10000:
        raise ValueError("BATCH_SIZE必须在1到10000之间")
    return value

这里明确允许缺失时用100；提供了非法值就直接报错，不会把它偷偷替换成默认值。数据库地址、必要凭证等不能缺少的配置，则应在启动时明确要求存在。把解析集中完成，后面的处理函数只接收已确认的整数，排查时也不用猜某个字符串从哪里来的。

凭证应从既有安全配置或环境读取，而不写进源码和可公开日志。环境变量也不是自动保密保险箱，运行平台的权限、进程信息和日志处理同样需要注意。
