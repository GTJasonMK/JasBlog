Python 27：浅拷贝与深拷贝：到底复制到了哪一层

Python运行机制与并发

目录

  • 赋值只增加引用，不会复制容器
  • 深拷贝不会把每一条引用都变成全新的对象
  • 实际任务常常只需要复制会变的那一部分

原列表还要保留，准备在副本上做修改，于是调用了 .copy()。新增一个外层元素时，两边确实互不影响；修改某个内层列表时，原数据却又变了。问题在于“创建了另一个容器”和“内部所有对象都独立”不是同一个承诺。

先把三种关系放在一个例子里：

python
import copy

original = [[1], [2]]
alias = original
shallow = original.copy()
deep = copy.deepcopy(original)
original[0].append(9)
print(shallow[0])  # [1, 9]
print(deep[0])     # [1]

最外面原本有一个列表，里面保存两个内层列表的引用。alias = original 只增加一个指向外层列表的名称；original.copy() 创建新的外层列表，但把里面的引用复制过去。所以 original[0] 与 shallow[0] 仍是同一个对象，append(9) 后两边都会看到 [1, 9]。

deepcopy 会按照对象的复制规则继续处理嵌套对象，这组普通列表中的内层列表也被复制，因此 deep[0] 仍是 [1]。它解决的是一份对象图中的共享关系，不能简单理解成“多复制了一遍列表”。

赋值只增加引用，不会复制容器#

如果对 shallow 执行 append([3])，只改变新的外层容器，原列表不会新增元素。若执行 shallow[0] = [7]，也只是替换副本外层的某个引用；若执行 shallow[0].append(7)，改的就是共享内层对象。

这几种写法看起来都从 shallow[0] 开始，但操作对象不同。排查问题时，先找到真正被修改的是哪一个对象，再看副本是否还引用它，比直接把所有复制替换为 deepcopy 更容易说明原因。

列表的 .copy()、list(original) 和 original[:] 都能在常见列表场景下创建一层浅拷贝。字典 .copy() 同样只复制外层映射，内部的列表或字典不会自动独立。

深拷贝不会把每一条引用都变成全新的对象#

如果原数据中两项有意指向同一个内层列表，深拷贝通常还会保留副本内部的这种共享：

python
shared = []
source = [shared, shared]
cloned = copy.deepcopy(source)

print(cloned[0] is cloned[1])  # True
print(cloned[0] is shared)     # False

deepcopy 使用记忆表记录已经处理的对象，避免对同一对象反复复制，也能处理一些循环引用。副本中的两条引用仍然指向同一个新列表，与原来的列表分开。

不可变对象通常可以安全复用，深拷贝也不保证每个对象的身份都会改变。自定义类可以规定自己的复制行为；文件、锁、网络连接等资源更没有通用的“复制出一份相同连接”含义。把含有资源的运行时对象整体深拷贝，常常要么失败，要么得到不符合预期的语义。

实际任务常常只需要复制会变的那一部分#

假设从缓存取到一条用户记录，只想给展示结果增加标签。可以明确创建需要独立的层：

python
user = {"name": "Ada", "tags": ["reader"]}
display_user = {**user, "tags": [*user["tags"], "python"]}
print(user["tags"])          # ['reader']
print(display_user["tags"])  # ['reader', 'python']

这里新的字典与标签列表都独立了，姓名字符串则可以复用。如果以后再添加嵌套的地址字典，这种写法并没有承诺地址也被复制，需要继续按修改范围检查。选择性复制的好处是规则可见，代价是要理解数据结构。

深拷贝适合确实需要独立的普通嵌套状态，比如建立一个用于后续试算的快照；它也要遍历更多对象并占用额外内存。只读数据不必为了“安全”每次都复制，大量共享的不可变结构也可能更合适。

复制还不能自动成为并发快照。如果另一线程正在修改源对象，复制过程中观察到的状态是否一致，仍需要锁或其他同步机制保证。它也不会替代数据库事务和版本检查。先定义哪一份状态要独立、在哪个时刻独立，再选择复制的层次，才不会把一种数据处理工具当成所有一致性问题的解法。
