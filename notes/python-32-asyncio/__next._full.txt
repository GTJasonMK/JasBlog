两个任务分别等待网络响应，程序不必在第一份响应到来之前一直闲着，可以先推进第二个任务。`asyncio`让这些等待在事件循环中交错进行，适合需要处理许多I/O任务的程序。它不会仅凭 `async` 关键字就把计算分散到多个CPU核心。

`async def` 定义协程函数，调用以后得到协程对象。这个对象描述一段可以被等待和调度的执行过程，不是已经拿到的结果。需要通过 `await` 或任务调度真正推进它。

## 连续等待与同时安排，是两种执行顺序

下面先定义一个用短暂停顿模拟I/O等待的任务，再把两项工作放进任务组：

```python
import asyncio

async def job(name):
    await asyncio.sleep(0.1)
    return name

async def main():
    async with asyncio.TaskGroup() as group:
        first = group.create_task(job("A"))
        second = group.create_task(job("B"))
    print(first.result(), second.result())

asyncio.run(main())
```

如果改成先 `await job("A")`，再 `await job("B")`，两次等待通常按顺序发生。任务组的 `create_task` 则把两项都交给事件循环调度，当A挂起等待时，B也有机会推进。

`await` 不保证每次都发生实际挂起：被等待对象若已完成，可能直接返回；它也不会把一个同步函数自动变成非阻塞函数。关键是等待的操作是否真正与事件循环协作。

示例从同步脚本用 `asyncio.run(main())` 创建并管理事件循环。Notebook和异步Web框架中可能已经有运行中的循环，此时应在现有上下文中 `await main()`，不能在同一个线程里随意再嵌套一次 `asyncio.run`。

## 任务组负责一起结束，不只是一起启动

Python3.11及以后提供的 `TaskGroup` 在退出上下文前会等待组内任务。某项发生普通异常时，会取消其余相关任务，并在等待清理后传播异常组。调用者能够知道这一组工作何时真正结束，不会把无人负责的后台任务留在外面。

原来的 `asyncio.gather` 也能等待多个可等待对象，并按输入顺序返回结果，但默认失败行为不同：一个普通异常传播给调用者时，其他任务不会因此自动全部取消。选择哪一个，要看失败后其他工作是否仍应该继续，以及由谁等待其结束。

## 超时通过取消协作，不是暂停键

在组外用 `asyncio.timeout` 限制这一阶段允许等待的时间：

```python
async def main_with_timeout():
    try:
        async with asyncio.timeout(1):
            async with asyncio.TaskGroup() as group:
                group.create_task(job("A"))
                group.create_task(job("B"))
    except TimeoutError:
        print("任务超时")
```

超时上下文通过取消当前任务并将相应取消转换为 `TimeoutError` 工作，所以上面的异常在上下文外捕获。它适合限制一段协程操作，而不是保证所有底层资源会在精确的一秒内被强行销毁。清理和不配合的阻塞调用仍会影响实际结束时间。

任务取消时，协程会在合适的执行机会收到 `CancelledError`。资源清理放在 `finally` 中；如果捕获了这个异常，清理后通常应该继续抛出，让调用方的取消语义成立。把取消吃掉并当成正常返回，会破坏任务组和超时机制依赖的生命周期约定。

## 同步阻塞不会因为放进协程就消失

在协程里调用 `time.sleep(1)`，事件循环线程就被它占住，其余任务也无法正常推进。改为 `await asyncio.sleep(1)`，才能在这段等待中把执行机会交还给循环。

HTTP、数据库和文件处理也要检查使用的接口。异步客户端通常可以在等待时挂起协程；已有同步I/O代码有时可以通过 `asyncio.to_thread` 放到受控线程中，避免阻塞事件循环。但取消等待不意味着底层线程立即停止，线程里的操作仍需要超时和清理。

持续占用CPU的计算也不会因为放进协程就让其他任务自然获得时间。计算型负载应评估进程池、原生库或拆分任务，而不是在外层多加几个 `async`。

任务数同样需要限制。对几十万条记录一次性创建任务，会为每个任务保留状态。信号量可以限制正在使用某个资源的任务数，队列和worker则能进一步限制待处理规模。异步处理省掉了大量等待时的闲置，不会免除连接、内存和依赖容量的限制。

可以把示例中的一个 `job` 改成明确抛出异常，检查另一个任务的 `finally` 是否完成；再把等待改长，检查超时能否传回外层。仅看到两行输出，无法证明这组任务在失败时也能退出。相关行为以[官方任务与取消说明](https://docs.python.org/3/library/asyncio-task.html)为准。
