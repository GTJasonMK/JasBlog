系统变慢以后，我会先找出单库究竟卡在哪里，再考虑增加组件。缓存、分析库和分片各自解决一部分负载，也各自增加同步、权限、故障恢复和数据核对的工作。

## 从工作负载选系统

| 需求 | 可考虑的系统 | 必须验证的代价 |
|---|---|---|
| 订单、库存、支付状态 | 关系型 OLTP | 事务竞争、索引写放大、恢复能力 |
| 可重建热点数据、短期协调 | Redis 等内存系统 | 淘汰、失效、持久化、主从切换语义 |
| 灵活文档结构 | 文档数据库或关系库 JSON | 访问模式、跨文档事务与约束 |
| 大范围聚合分析 | 列式分析库、数仓 | 数据延迟、导入成本和修订方式 |
| 全文与相关性检索 | 搜索系统 | 索引更新延迟与重建能力 |

先选一个明确事实来源。把金额同时交给两个系统独立更新，会增加对账和冲突处理，不能用“最终一致”省略修复机制。

## 缓存的一致性边界

cache-aside 通常先读缓存，未命中再读数据库并回填；更新先提交数据库，再使缓存失效。但并发读取可能在失效后又把旧值回填，失效消息也可能失败。

TTL 限制陈旧持续时间但不提供强一致。延时双删没有天然覆盖所有执行顺序。需要结合事务后可靠失效、版本比较、短期陈旧容忍和周期核对设计；余额与下单资格等强规则以权威事务状态判断。

热点过期可能让大量请求同时打到数据库，可使用请求合并、分散到期时间和受控刷新。对不存在对象的短期缓存要限制键数量并结合限流，避免外部输入造成无界内存消耗。

## 分析任务与 CDC

大范围报表会争抢 OLTP 的 CPU、I/O 与缓存。先优化 SQL 和索引，再评估只读副本或数仓。副本仍有复制延迟，长报表还可能与回放冲突。

CDC 把数据库变化传给下游时，需要初始快照与增量位点衔接、断点保存、重复处理、顺序和 schema 演进。下游接收成功不代表业务已应用成功，应明确提交点并让消费者幂等。

修复历史数据不能只重跑整个任务而忽略已计费或已发送的副作用。按批次保存输入版本、处理位点和结果，输入变化时只重做受影响部分。

## 扩展前先找到瓶颈

查询慢先查扫描、计划、索引和返回量；连接压力先查池和长事务；写入热点先查锁与事务范围。垂直扩容、读副本、归档和分区常比跨库分片更容易管理，但都需要证据。

分片把同一业务数据分散到独立数据库后，原来的本地外键、唯一性、连接、事务、排序和备份切点都可能失去直接支持。分片键决定热点与路由，扩容还需要迁移和重平衡。跨服务拆分同样增加网络失败、部署和数据一致性成本。

Saga、补偿和 outbox 可以组织跨系统流程，但补偿可能失败，已发货也不能简单撤销。先定义可逆与不可逆动作、状态机、超时和人工处理，再选择技术。

## 动手验证

为示例项目写一页选型说明：为什么订单事实留在关系库，哪些查询可缓存，何时引入分析副本，什么测量结果才足以考虑分片。每项说明数据延迟、故障与恢复责任。

参考：[PostgreSQL 逻辑复制](https://www.postgresql.org/docs/16/logical-replication.html)、[Redis 文档](https://redis.io/docs/latest/)。
