比较数据库之前，我会先写清楚需要一起提交哪些记录、主要怎么查、允许多少延迟，以及故障后要怎样恢复。有了这些条件，产品的能力和限制才有比较依据。

下面比较 33 种数据库、扩展和云服务，也包括缓存与搜索引擎。涉及一致性和扩展的机制，可以回看[缓存与分布式选型](/notes/database-22-cache-distribution)，官方入口集中在[资料索引](/notes/database-references)。

## 先问业务需要什么

“哪种数据库最好”缺少评价条件。先写清以下要求，产品优缺点才有比较依据：

| 要求 | 要问的问题 | 会怎样改变选择 |
|---|---|---|
| 正确性 | 哪些记录必须一起提交？能容忍多少秒旧数据？ | 决定事务边界、读取一致性和副本路由 |
| 查询方式 | 按主键查、跨表关联、全文搜索、时间聚合，还是向量近邻？ | 决定数据模型、索引与执行方式 |
| 实际负载 | 每秒读写量、峰值并发、热点键、数据增速和延迟目标是多少？ | 决定单机能力、分区、扩容与资源预算 |
| 故障目标 | 丢一台机器或一个可用区时，允许丢多少数据、停多久？ | 决定副本位置、提交策略、备份和切换流程 |
| 团队与成本 | 团队会维护什么？能接受哪些授权、托管和迁移成本？ | 决定方案是否能长期运行，而不只是能部署 |

同样是 1 TB 数据，每次按键读一行与每次扫描全年销售，适合的执行方式不同。记录总量不能单独决定选型。关系、文档、搜索、向量等能力也会在同一产品中重叠，应优先验证已有系统能否满足需求。

## 一、通用关系型数据库

关系型数据库适合维护明确结构、跨表关系与业务事务。下面产品都能处理企业业务，具体差别来自 SQL 能力、存储机制、生态、授权和运维方式。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| PostgreSQL | 事务、约束、复杂 SQL、JSONB 与 PostGIS 等扩展可以配合使用 | 需要维护 VACUUM、统计、连接和扩展升级；水平写扩展需要额外架构 | 订单、账务类事务、复杂业务查询、地理数据，或已有 PG 技术积累的团队 |
| MySQL，重点是 InnoDB | 支持事务与按键、范围访问；Web 驱动、管理工具和托管产品选择较多 | 要理解隔离与范围锁；复杂 SQL 需检查实际计划；读副本不会自动扩展主库写入 | 电商、账号、内容管理、常规 Web 业务，或已有 MySQL 运维体系的团队 |
| MariaDB | 与 MySQL 有共同历史，支持关系型事务和多种存储引擎，可复用部分工具经验 | 与 MySQL 在 SQL、JSON、GTID、复制和工具上存在差异，升级与迁移要逐项核对 | 已采用 MariaDB 的业务、需要其具体功能的自建关系库项目 |
| Oracle Database | SQL、PL/SQL、RMAN 备份恢复及主备工具可覆盖复杂企业应用 | 商业版本与选件授权需要核算；对象、过程和运维体系迁移成本可能较高 | 已有 Oracle 应用、依赖大量 PL/SQL 的系统，以及需要对应企业功能与支持的项目 |
| SQL Server | T-SQL、管理工具与微软数据工具链便于配合 .NET、报表和企业应用 | 授权、版本及 Windows/Linux 功能差异要核对；T-SQL 与其他数据库不完全通用 | 微软技术栈、已有 SQL Server 的 ERP、业务后台和报表系统 |
| SQLite | 进程内运行，无需独立服务，单文件便于分发，支持事务 | 同一数据库文件的写入需要串行协调；跨主机共享文件、多用户高写并发需要特别评估 | 桌面软件、手机、设备、本地任务状态和单机应用数据 |
| 达梦 DM | 提供事务、备份、管理和迁移工具，可结合国产平台适配及本地服务要求评估 | 具体 SQL、数据类型、过程、驱动和高可用功能要按版本验证；需要计入授权与培训成本 | 有明确平台适配、采购或交付要求的业务，以及经过验证的 Oracle 等迁移项目 |
| 人大金仓 KingbaseES | 提供企业关系库能力、兼容与迁移方案，可按国产平台和厂商服务要求选型 | 兼容模式、扩展、存储过程与应用驱动需逐项验证；不能把不同产品版本视为同一能力集合 | 有国产化交付要求、既有应用适配方案和厂商支持条件的项目 |

**如何在 PG 与 MySQL 之间选择。** 两者都能承载常规订单事务。已有团队经验、托管条件与真实查询计划通常比抽象性能排名更有价值。大量复杂 SQL、地理数据或现有 PG 扩展需求，可以优先评估 PG；已有 MySQL 应用、复制、备份和发布流程，可以优先验证沿用 MySQL。详细行为差异见[第 21 章](/notes/database-21-mysql)。

**如何理解 SQLite 的适用范围。** 它可以用于正式产品。是否合适取决于访问与部署方式：本地应用保存自己的业务数据很合适，多台应用服务器同时修改网络共享目录中的一个文件则需要重新评估。WAL 模式可以改善读写并发，但不会让同一数据库获得任意数量的并发写入者。

**如何评估存量迁移。** 不能只比较表结构和几条 SELECT。还要验证序列、排序规则、空字符串与 NULL、时间、金额、锁、存储过程、驱动、CDC、备份和故障切换。Oracle 或 MySQL 兼容模式只覆盖其说明的范围，完整方法见[第 20 章](/notes/database-20-migrations)。

## 二、分布式 SQL 数据库

这类数据库把数据分布到多个节点，同时提供 SQL 和事务能力。它们可以减少部分应用分库分表工作，也会引入多副本共识、网络通信、重试和集群管理成本。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| TiDB | MySQL 协议兼容、分布式事务与水平扩展；可通过相应组件组织事务和分析负载 | SQL 与 MySQL 仍有差异；跨节点事务、热点与数据调度需要测量；集群资源成本增加 | 单库容量或写入扩展已出现实际瓶颈，希望保留 SQL 并评估 MySQL 应用迁移的业务 |
| OceanBase | 提供分布式事务、多副本与租户资源管理，具有相应 SQL 兼容模式 | 兼容模式及功能取决于所选版本和产品；分区、租户、资源与故障管理需要专门经验 | 对容量、可用性和资源隔离有要求，且已完成 MySQL 或 Oracle 应用兼容验证的业务 |
| CockroachDB | 分布式事务与数据复制，使用 PostgreSQL 协议生态，提供多地域数据布局能力 | PG 协议不代表所有 PG 扩展和 SQL 都兼容；地域布局影响延迟、故障能力和重试率 | 需要 SQL 事务、节点扩展与多地域部署，并能按其事务和数据布局要求开发的业务 |

跨地域强一致提交往往需要跨地域通信。副本放得更远，提交延迟和故障处理条件也会变化。必须同时测试正常流量、热点、节点故障和网络分区，不能只验证加节点后的总吞吐。

这组笔记订单库的数据规模尚不足以证明需要分布式 SQL。先完成查询、索引、事务与容量测量，再说明单库方案具体在哪个目标上无法满足要求。

## 三、内存键值数据库与缓存

这类系统适合按键访问热点数据。低延迟的代价通常是内存容量、淘汰策略、持久化与故障切换边界。对于缓存，首先要明确数据丢失后能否从权威来源重建。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| Redis | 字符串、哈希、集合、有序集合和 Streams 等结构可表达计数、排行及短期状态 | 内存、热键、大键和阻塞命令会影响延迟；RDB/AOF 与副本配置决定数据损失边界；集群跨槽操作有限制 | 缓存、排行榜、限流、会话和可重建短期状态；严格业务规则需另验一致性 |
| Valkey | 提供内存数据结构、持久化和复制，可评估复用相关协议与客户端生态 | 与 Redis 各版本的命令、模块、集群和功能演进要分别核对；同样需要管理内存及故障语义 | 需要社区维护方案，并已验证所需命令、驱动和运维功能的缓存与键值业务 |
| Memcached | 键值缓存模型和接口简单，便于存储可重新计算的查询或页面结果 | 标准使用方式不提供 Redis 式持久化与数据结构；应用需要处理失效、节点变化与缓存未命中 | 简单对象缓存、页面片段缓存、容易从数据库重建的结果 |

Redis 的一次原子扣减只保护该实例内相应操作，无法自动把订单库写入、外部支付与故障切换一起纳入原子事务。用于库存预扣或分布式锁时，要额外定义幂等、租约、失败恢复和对账。缓存一致性的具体过程见[第 22 章](/notes/database-22-cache-distribution)。

## 四、文档数据库

文档模型把相关属性组织到一个文档中，适合围绕完整业务对象读写。字段可以灵活变化，但类型、必填项、版本演进和索引仍需要明确规则。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| MongoDB | 文档可嵌套相关数据，支持索引、聚合与多文档事务，可按文档访问模式组织数据 | 多文档事务有部署和性能条件；无界数组、跨文档关联和重复事实增加维护成本；分片键需要提前评估 | 属性差异较大的商品资料、内容、业务文档，以及主要按完整对象读取的业务 |

MongoDB 的单文档写入具有原子性，多文档事务也受支持，具体语义取决于部署及读写关注配置。设计时仍要控制文档大小、数据复制和跨文档修改范围。

只有少量可变属性时，也可以先评估 PostgreSQL JSONB 或 MySQL JSON。是否引入 MongoDB，应由文档访问方式、索引、更新与扩展需求证明。

## 五、宽列数据库

宽列数据库常按分区键和行键组织访问。“宽列”描述数据模型，分析数据库的“列式存储”描述物理存储方式，两者分类维度不同。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| Apache Cassandra | 数据分区与多副本支持横向扩展，可按业务选择相关一致性配置 | 需要围绕查询和分区键建模；跨分区关联、任意筛选与复杂事务不能按关系库方式预期；还需修复和压实维护 | 写入量大、查询模式固定的事件、设备记录和按用户或时间桶组织的数据 |
| Apache HBase | 按 RowKey 排序，提供大规模表的实时点查、范围访问及行级一致性能力 | RowKey 不当会产生热点；跨行事务与复杂 SQL 通常需要额外方案；依赖底层存储与集群运维 | 已有 Hadoop/HBase 体系、需要大规模稀疏表和按键范围访问的业务 |

这类系统适合先知道如何查，再围绕访问路径组织数据。分区过大或全部新记录写向同一个键范围，会让扩容后仍然出现热点。单分区条件操作也不能直接推导成任意跨分区事务保证。

## 六、云托管键值与文档数据库

托管服务减少了服务器管理工作，仍需要设计分区、权限、一致性、备份和预算。跨区域复制及跨分区事务的范围必须按照具体接口和配置确认。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| Amazon DynamoDB | AWS 托管键值与文档访问，提供条件写入、事务 API 和扩展能力 | 分区键、二级索引与访问模式约束设计；扫描和容量使用影响费用；不同读取与全球表模式保证不同 | AWS 上按键访问为主、流量变化大、希望减少自建集群管理的业务 |
| Azure Cosmos DB | 提供多区域数据分布、不同一致性级别与相应 API 生态 | 需要评估分区键、RU 请求单位成本与跨分区查询；事务和功能范围依所选 API 与配置而异 | Azure 生态下需要多区域访问、低延迟文档或键值读取的应用 |

RDS、Cloud SQL、Azure Database for PostgreSQL 等主要是运行特定引擎的托管方式，需要同时选择引擎与服务配置。Aurora 有自己的实现与兼容范围，也要单独核对。托管服务不会自动替你确认业务授权、备份可恢复性、SQL 成本和应用重试是否正确。

## 七、搜索与日志检索引擎

搜索引擎通过倒排索引、分词和相关性排序组织检索，适合“找到符合含义或关键词的内容”。写入后的可搜索时间、分片数量、索引映射与重建流程都属于选型条件。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| Elasticsearch | 全文检索、相关性排序、过滤、聚合，以及日志和可观测性工具可以配合 | 索引与副本占空间；刷新和段合并消耗资源；映射变更可能需要重建；跨文档业务事务需另行设计 | 商品与站内搜索、日志检索、可观测性、文本及混合检索 |
| OpenSearch | 提供搜索、聚合、向量能力及 Dashboards 等配套，可自建或使用相应托管服务 | 与 Elasticsearch 已分别演进，客户端、插件和索引版本不能假定互换；同样有分片、内存和重建成本 | 已有 OpenSearch 生态、需要相应搜索与日志能力的团队 |

订单提交后可以异步更新搜索索引，并接受明确的短暂搜索延迟。订单是否付款、还能否取消等业务判断，应读取维护这些规则的权威状态。搜索索引与源库之间还需处理重复事件、删除同步和重建期间的数据追平。

## 八、分析数据库与云数仓

分析查询经常读取大量记录中的少数列。列式读取、压缩和批量计算可以减少这类工作量；高频逐行改写、短事务和大量小请求则需要另外验证。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| ClickHouse | 列式存储、压缩与批量计算适合事件和日志的大范围聚合 | 表引擎、排序键、分区和合并策略影响效果；更新删除及其可见性取决于具体机制；不能直接套用 OLTP 写模型 | 埋点、日志、用户行为、监控分析、实时聚合报表 |
| Apache Doris | MPP 分布式分析、SQL 关联与聚合，可按明细、聚合、唯一键等表模型组织数据 | 表模型与分桶需要设计；导入、更新合并、物化视图和资源隔离有维护成本 | 实时报表、业务分析、交互查询和需要关联多张业务表的分析应用 |
| StarRocks | 向量化执行、关联分析、物化视图与湖数据查询能力可组合使用 | 节点、数据分布、导入和物化视图需管理；不同部署形态成本不同，需用实际 SQL 验证 | BI、多表交互分析、数据湖查询加速、面向用户的分析服务 |
| DuckDB | 进程内分析，便于用 SQL 读取 Parquet、CSV 等文件，无需另建分析服务 | 单机资源、并发写入和多进程协作有边界；作为共享服务需要额外的接入与资源管理 | 本地数据分析、Python 数据处理、离线报表和 Parquet 数据探索 |
| Snowflake | 托管分析平台，存储与计算资源可分别管理，便于数仓、共享和并发分析 | 仓库运行、存储、数据传输等需控制预算；常规分析表与特殊事务表的能力要分开核对 | 企业数仓、多团队 BI、数据共享和已有 Snowflake 生态的分析平台 |
| BigQuery | 托管大规模 SQL 分析，减少自建分析集群工作，可结合 GCP 数据工具 | 扫描量、容量模式和存储影响费用；分区、聚簇及查询方式决定成本；频繁小更新需验证 | GCP 数仓、大规模日志与事件分析、批量 BI 和数据探索 |

ClickHouse、Doris 和 StarRocks 都需要用真实数据分布、关联方式、导入速率及并发 SQL 比较。它们支持的更新、点查与事务能力不断演进，不能从产品类别直接推断某个操作绝对不能执行。

分析系统接入订单数据后，要明确快照与 CDC 衔接、更新删除、重复去重、迟到数据和金额口径。查询快但重复计算订单，不能满足报表要求。报表语义可以回看[关联与汇总](/notes/database-05-joins-subqueries)和[窗口函数与报表](/notes/database-06-windows-reports)。

## 九、时间序列数据库

时序负载通常包含时间、对象标识、标签与测量值，常见操作包括持续写入、按时间范围聚合、降采样和按保留期清理。

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| InfluxDB | 围绕时间序列采集、查询和保留组织数据，适合持续测量与监控 | 1、2、3 代产品在引擎、查询语言和部署功能上有差异；标签基数、保留期和迁移要按具体版本评估 | 设备传感器、基础设施指标、工业测量与时序看板 |
| TimescaleDB | 基于 PostgreSQL 扩展时间分区和时序分析，可结合关系表、SQL 与相关聚合能力 | 仍需维护 PG；扩展升级、保留策略及不同功能的授权范围要核对；时序与业务负载可能争用资源 | 需要将测量值与客户、设备、订单等关系数据关联的时序应用 |

“每个请求 id 都作为标签”可能让标签组合大量增长，具体影响取决于引擎版本和索引模型。选型测试应保留真实标签分布、乱序写入、补历史与保留清理，不能只测规则生成的顺序时间点。

## 十、图数据库

| 产品 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| Neo4j | 属性图和 Cypher 便于表达多跳关系、路径、关联模式与图遍历 | 图模型和语言需学习；超高连接度节点及无界遍历会放大工作量；集群、授权及分析能力依版本核对 | 反欺诈关系、知识关系、依赖分析、社交关系与路径查询 |

只有“一个订单属于一个客户”这样的常规关系，关系库关联就能处理。图数据库的价值要通过真实路径与模式查询证明，同时限定遍历深度、结果量和热点节点。图数据若来自交易库，还要管理同步延迟和删除传播。

## 十一、向量检索数据库与扩展

向量检索用于寻找与一个向量接近的记录，常与元数据过滤和文本检索结合。近似索引通过减少搜索工作换取速度，需要同时评估召回率、延迟、空间和更新成本。

| 产品或扩展 | 主要优点 | 限制与代价 | 适用场景 |
|---|---|---|---|
| pgvector | 在 PostgreSQL 中存储向量，结合事务、SQL、关系过滤和精确或近似检索 | 索引构建、内存与查询和业务库争用资源；过滤后的召回率、更新成本和扩展版本需测试 | 已有 PG，希望将业务元数据与向量放在同一事务和查询体系中的检索应用 |
| Milvus | 面向向量检索提供索引与部署选择，可评估独立扩展检索负载 | 部署形态决定组件与运维成本；一致性级别、数据导入、索引和标量过滤需要调优 | 向量规模、吞吐或检索负载已需要独立管理的图文、语义与相似度检索 |
| Qdrant | 向量检索可结合 payload 元数据过滤，提供 API 与自建或托管方式 | 索引、复制、持久化、过滤和分片仍需要容量规划；通常要维护与业务事实来源的同步 | 带结构化过滤的语义搜索、相似商品检索、多租户检索应用 |

向量库的记录数量不能单独作为选择阈值，还要看维度、索引、过滤选择性、召回率、更新量和硬件。检索效果也受向量模型与距离度量影响，不能把模型变化造成的差异全部归因于数据库。

同时明确租户权限、删除传播、原文版本与向量版本的对应关系。保存相似向量不会自动维护订单、付款和库存等业务约束。

## 按具体场景做选择

下面是候选方案和验证方向，并不要求把表中组件全部部署。

| 场景 | 可以先评估的方案 | 决定是否采用的证据 |
|---|---|---|
| 中小电商的订单与库存 | PG 或 MySQL；查询压力确有需要时再评估缓存 | 下单不变量、事务延迟、热点竞争、备份恢复，以及团队维护能力 |
| 本地桌面软件与设备 | SQLite 保存事务状态；本地文件分析可评估 DuckDB | 写入并发、文件访问方式、崩溃恢复和部署限制 |
| 商品属性经常变化 | 现有关系库的 JSON 能力或 MongoDB | 主要按完整商品读取还是频繁跨表关联，字段校验、索引与批量修改是否方便 |
| 商品全文搜索 | Elasticsearch 或 OpenSearch，加上维护订单事实的关系库 | 分词质量、相关性、可接受的索引延迟、索引重建和删除同步 |
| 设备测量与时间看板 | InfluxDB；需要关联业务表时评估 TimescaleDB | 标签分布、乱序补写、时间聚合、保留策略与扩展运维成本 |
| 大量行为与销售分析 | ClickHouse、Doris、StarRocks；云环境还可评估 Snowflake 或 BigQuery | 真实关联 SQL、导入与更正、并发、数据时效和完整费用 |
| 已确认单库写入或容量不足 | TiDB、OceanBase 或 CockroachDB 等候选 | 与现有 SQL 的差异、分布式事务延迟、热点、故障演练和总成本 |
| 多跳风控关系 | Neo4j，简单关联也可先验证关系库 | 有界路径查询的表达与执行代价，数据同步和关系变更频率 |
| 已有 PG 的知识检索 | 先评估 pgvector，再依据测量比较 Milvus、Qdrant | 固定召回目标下的过滤效果、延迟、写入、隔离与恢复成本 |
| 存量企业系统迁移 | 现有引擎升级、相应托管服务，或经过适配验证的替代产品 | SQL 与过程兼容、应用回归、数据一致、业务窗口、授权及退出方案 |

例如示例订单项目，先让 PG 负责订单、库存与流水。数据量小时，普通汇总也可以在受控条件下由 PG 完成；出现全文搜索需求后再评估搜索索引；分析负载确实影响事务目标时，再增加分析系统。每多维护一份数据，都要增加同步、权限、恢复和一致性核对。

## 企业选型的最小验证清单

从满足硬性要求的产品中选两个候选，用相同数据和业务操作完成一次验证：

1. **固定范围。** 写清产品版本、版本分支、部署形态、授权、数据模型和硬件预算，保存配置。
2. **核对语义。** 覆盖金额、时区、排序、唯一性、事务、并发冲突和重试，确认结果符合业务规则。
3. **测量负载。** 使用真实分布、热点、读写比例和并发，记录 p95/p99、错误率、吞吐、资源与费用。
4. **制造受控故障。** 验证断连、节点不可用、重试、备份恢复和数据追平，记录实际恢复点与时间。
5. **验证迁移与退出。** 检查驱动、存储过程、DDL、CDC、导入导出、回滚依据，以及未来换产品的成本。
6. **比较总成本。** 除服务器外，计算存储、副本、备份、网络、授权、托管请求、值班、升级和培训。

不要给每个优点随意打分后求和。先淘汰不满足事务、合规、部署或恢复硬性条件的方案，再比较剩余候选的可测成本。授权和商业功能会随版本变化，正式采用前按对应产品和合同核对。
