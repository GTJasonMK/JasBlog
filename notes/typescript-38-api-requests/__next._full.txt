请求失败后返回空数组，页面显示暂无任务，用户会以为之前的数据没了。失败被改写成正常数据，连重试入口也失去依据。状态首先要保留真实含义，再决定怎样显示。

请求函数负责协议细节，页面负责展示状态。请求结果应使用明确的联合类型，避免用多个布尔值组合出不可能状态。

~~~ts
type LoadState<T> =
  | { kind: "loading" }
  | { kind: "ready"; data: T }
  | { kind: "error"; message: string };
~~~

检查 response.ok，解析错误结构；处理取消请求和组件卸载。用一个小型 API client 统一 base path、credentials 和错误解析，但不要隐藏关键失败。

loading没有当前结果，ready一定有data，error一定有message。对于任务数组，空与非空都属于ready，只是data.length不同；不能把error也塞成ready空数组。switch按kind呈现以后，检查器能帮助避免在loading时读取尚不存在的数据。

35章的Hook负责执行这个转换，请求函数负责HTTP与Schema解析，页面只看状态。API client集中已有共同协议，不必为每条接口再造一层同形包装，也不能把404、坏JSON与网络失败统一吞掉。

## 刷新时是否保留旧内容

初次加载没有数据，可以显示等待；刷新已有列表时，有时希望旧结果继续可见，同时提示正在更新。那应明确增加“已有数据且刷新中”的状态关系，而不是任意组合loading、hasData、error三个布尔值，最后出现相互矛盾的界面。

相同资源的请求要识别当前版本。参数改变或用户重试时，前一次响应可能晚到，取消与身份核对保证旧结果不会覆盖新页面。取消是当前交互不再需要结果，通常不应作为需要用户处理的错误弹窗；真正失败则保留可重试信息。

错误文案按原因帮助下一步：未登录引导重新确认会话，无权限说明访问受限，暂时不可用提供重试。内部堆栈留在受控日志，不能把数据库异常原文直接展示。重试是否安全，尤其写入请求，要由接口合同决定。

## 保留失败，才能决定下一步怎么做

- fetch 不会因为 404 自动抛错。
- 服务端返回结构要在边界验证，不能假定 JSON 一定符合类型。
- 不要把请求错误静默改成空列表，避免假成功界面。

测试至少覆盖延迟响应、成功空列表、成功有数据、HTTP失败、结构错误和旧响应晚到。每一份输入对应明确页面状态，才能证明用户看到的内容与请求实际结果一致。

实现任务列表加载状态，区分空数据和加载失败，并提供重试按钮。
