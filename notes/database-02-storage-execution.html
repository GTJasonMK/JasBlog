数据库 02：一条 SQL 从执行到落盘经历了什么

数据库PostgreSQL

  • 三种容易混淆的“日志”

UPDATE返回了，COMMIT也成功，数据库却不必立刻把每一张修改页都写回原位置。听起来像数据没保存，其实提交所依靠的首先是日志。理解这条路径，才能同时解释查询为什么慢、崩溃后又怎样恢复。

一条 SELECT 如何运行#

服务器解析语法、解析表和列名、检查权限，再由优化器选择执行计划。执行器根据计划读取页、过滤行、完成连接和排序，最后返回结果。预备语句可能复用部分处理结果，不能据此假定每次都重新产生最适合当前参数的计划。

同一份SQL可能顺序扫描，也可能先走索引；选择依据来自统计估算与成本模型。某个客户占了大半订单，平均分布假设就可能失真，进而选错连接或扫描方式。结果语义与访问代价分开判断，才能避免用“查出来了”证明计划合适。

数据如何落到磁盘#

PostgreSQL 表通常以堆文件存储，分成固定大小的页，默认页大小一般是 8 KB，实际值可查询 SHOW block_size。索引是单独的数据结构，保存键与定位信息。普通主键不会把堆表永久按主键顺序排列。

读取先经过 PostgreSQL 的共享缓冲区，也可能命中操作系统页缓存，最后才读磁盘。所以执行计划中的 shared read 表示数据块读入共享缓冲区，不等于一次物理磁盘读取。

即使命中内存，扫描百万行、比较文本和排序仍要CPU与内存。缓存减少一部分I/O，不会把多余工作消除；先看读了多少块、处理多少行，再判断是否需要改查询。

sql
SHOW block_size;
SHOW shared_buffers;
SELECT pg_size_pretty(pg_relation_size('shop.orders')) AS heap,
       pg_size_pretty(pg_indexes_size('shop.orders')) AS indexes,
       pg_size_pretty(pg_total_relation_size('shop.orders')) AS total;

total 还可能包含 TOAST 等附属存储。小表占用页数受最小分配和索引结构影响，不能用三行数据推断每行平均生产成本。

一条 UPDATE 如何持久化#

更新通常形成新的可见行版本，旧版本暂时留给仍需要它的事务。对应内存页变脏，恢复所需变化先进入WAL；默认同步提交等待相关WAL持久化，数据页稍后写回。崩溃后根据日志重放，就能恢复那些已确认而尚未全部写回页的变化。

发生崩溃时，系统利用 WAL 恢复一致状态。检查点推进恢复起点，缩短需要重放的范围。检查点频繁会增加写入压力，过少则可能增加恢复时间和 WAL 占用。

WAL保留还受归档与复制槽等因素约束，不能只改检查点就保证磁盘不增长。提交成功也依赖刷盘设置与存储兑现承诺，关闭保护后测出的速度不能套回原来的持久性结论。

提交返回成功的持久性取决于数据库设置与存储真实兑现刷盘。不能通过关闭 fsync 获得可用于企业承诺的性能数据。synchronous_commit=off 也会改变最近已确认事务在崩溃时的丢失风险。

三种容易混淆的“日志”#

类型用途无法替代的部分
WAL崩溃恢复、物理复制、PITR不直接记录业务审批与操作者意图
SQL / 审计日志查慢语句、访问者和操作过程不能当成完整数据库备份
业务流水解释支付、库存、账务变化需要与业务事务保持一致，不能自动修复底层损坏

PostgreSQL 通过堆中的行版本提供 MVCC；MySQL InnoDB 主要通过 undo 链提供历史版本。两者都有重做日志，但内部对象和清理机制不同。

WAL回答系统怎样恢复，业务流水回答库存为何减少，两者记录的事实层次不同。查到一条库存更新日志，仍不等于知道它属于哪张订单、是否经过授权；后面的事务项目会把这些业务事实一并留下。
