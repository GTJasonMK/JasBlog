商品有编号、名称和价格，分散成三个数组，很容易在增删时失去对应关系。结构体先解决的是“这些字段共同描述一个对象”。至于价格来自数据库还是测试数据，则是另一个变化点。

## 结构体与组合

结构体把有关联的字段放在一起。Go 常通过嵌入和组合复用行为，而不是建立深层继承树。

~~~go
type Product struct {
	ID    int64
	Name  string
	Price int64 // 以分为单位
}
~~~

真实 API 中还要考虑字段校验、数据库模型和对外响应是否应该使用不同类型，避免把内部字段意外暴露。

Price以分为单位，但字面量仍能填负数。结构体组织字段，不会自动建立业务不变量；需要时用构造函数和修改方法检查规则，并收紧内部字段的可见范围。

组合让对象持有另一个对象；嵌入还会提升部分字段与方法，但不等同于类继承。嵌入很大的外部类型，可能意外公开许多方法，普通命名字段通常更容易控制API范围。

## 接口

接口由方法集合定义，类型无需显式声明“实现了接口”。依赖方通常定义小接口，只暴露自己需要的能力。

~~~go
type PriceReader interface {
	PriceByID(ctx context.Context, id int64) (int64, error)
}
~~~

如果接口只有一个实现且没有测试或边界需求，不要过早抽象。接口的价值在于明确调用者需要什么，并允许替换外部依赖。

PriceReader可以定义在消费价格能力的包里，只要求一个方法。数据库实现有再多管理功能，订单业务也只看这一项能力；测试则提供固定价格或明确失败的实现，不必先启动数据库。

接口只检查签名，不检查语义。返回负价格、忽略context或吞掉查询错误的实现，即使编译通过，也可能违背调用方约定。替身必须保留相同的成功、缺失和失败含义。

接口值同时包含动态类型和值。把一个 nil 指针赋给接口后，接口本身通常不等于 nil；这类 typed nil 是常见陷阱。判断接口错误时应直接用 err == nil、errors.Is 或 errors.As，而不是自行比较内部值。

因此返回error时，成功分支直接 `return nil`，不要把值为nil的自定义错误指针装进接口。调用方看到非nil接口会认为失败，与内部指针是否为空不同。

## 泛型

泛型适合编写对多种类型都成立的通用算法和容器。若业务类型有不同规则，普通接口和专用函数通常更容易读。不要为了“泛型化”而把简单逻辑变复杂。

例如位置查找只依赖相等比较，可以保留元素类型：

~~~go
func Index[T comparable](values []T, target T) int {
	for index, value := range values {
		if value == target {
			return index
		}
	}
	return -1
}
~~~

`comparable` 允许相等比较，-1表示没找到。整数与字符串可用同一算法；元素本身不可比较时则不能套用。标准库已有相应切片查找工具，项目中先复用，这段用于理解约束。

接口描述运行时需要的行为，泛型保留编译时类型关系。两者可以配合，但不必把商品价格和用户积分仅因为都含数字就合成一个泛型业务函数。
